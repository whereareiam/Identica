`identity/username/conflicts.yml` содержит правила, которые решают, что делать, когда два аккаунта хотят один ник, а `identity/username/messages.yml` — то, что при этом видят игроки. Когда возникает конфликт и что делают правила по умолчанию, описано в разделе [Ники и конфликты](../../../admins/guides/accounts/usernames/index.mdx).

## conflicts.yml

<Tabs items={["YAML", "JSON"]}>
  <Tab value="YAML">
```yaml
outcomes:
  rename-holder:
    pattern: "{username}_{provider}"
    tooLong: SHORTEN
    taken: NUMBER
    holderOnline: KEEP_PLAYING
  rename-arriving:
    pattern: "{username}_{provider}"
    tooLong: SHORTEN
    taken: NUMBER
  refuse: {}
providers: {}
rules:
  - arriving: { guarantees: [OWNED_USERNAME] }
    holder: { guarantees: [] }
    trigger: FIRST_JOIN
    outcome: rename-holder
  - arriving: { guarantees: [OWNED_USERNAME] }
    holder: { guarantees: [] }
    trigger: PROVIDER_RENAME
    outcome: rename-arriving
  - arriving: { guarantees: [] }
    outcome: refuse
  - outcome: refuse
```
  </Tab>

<Setting
  name="rules"
  takes="список правил"
  affects="какой исход решает конфликт"
>

Правило без условий — наименее конкретное: оно решает всё, что не решает ни одно другое правило.

</Setting>

#### Какое правило применяется [#which-rule-applies]

Из правил, подходящих к конфликту, побеждает самое конкретное:

1. правило, называющее id провайдеров для большего числа сторон, сильнее правила, называющего их для меньшего;
2. затем правило, называющее гарантии для большего числа сторон, сильнее правила, называющего их для меньшего;
3. затем правило, которое дополнительно задаёт `trigger` или `arrivedVia`, сильнее правила без них.

Из одинаково конкретных правил побеждает первое в списке. Если два одинаково конкретных правила могут подойти к одному конфликту, но решают его по-разному, консоль предупреждает об этом при запуске и перезагрузке, потому что второе там никогда не применится. Если не подходит ни одно правило, входящему игроку отказывают.

#### rules[].arriving и rules[].holder [#rulesarriving-and-rulesholder]

Что правило требует от провайдера заходящего игрока и от провайдера держателя. Не указывайте сторону, чтобы принять любую.

<Setting
  name="guarantees"
  depth={5}
  takes="список гарантий, например `[OWNED_USERNAME]`"
  affects="на каких провайдерах может стоять сторона"
>

Провайдер должен иметь ровно эти гарантии: `[]` требует провайдера без гарантий, например Credential. Не указывайте поле, чтобы принять любого провайдера. `OWNED_USERNAME` — гарантия провайдеров, которые владеют никами своих игроков, например Premium.

</Setting>

<Setting
  name="providers"
  depth={5}
  takes="список id провайдеров, например `[premium]`, в любом регистре"
  affects="на каких провайдерах может стоять сторона"
>

</Setting>

<Setting
  name="rules[].trigger"
  depth={4}
  takes="`FIRST_JOIN` или `PROVIDER_RENAME`"
  affects="к какой ситуации относится правило"
>

Не указывайте, чтобы правило относилось к обеим. См. [Когда возникает конфликт](../../../admins/guides/accounts/usernames/index.mdx#when-a-conflict-comes-up).

</Setting>

<Setting
  name="rules[].arrivedVia"
  depth={4}
  takes="причину, по которой был выбран провайдер заходящего игрока, например `HOSTNAME`"
  affects="относится ли правило только к игрокам, попавшим к провайдеру таким путём"
>

`HOSTNAME` означает, что игрок зашёл через одну из `entrypoints` провайдера. Не указывайте, чтобы принять любую причину.

</Setting>

<Setting
  name="rules[].outcome"
  depth={4}
  takes="id исхода, например `rename-holder`, или `{ id: ..., with: { ... } }`, чтобы изменить часть его настроек только для этого правила"
  affects="как решается конфликт"
>

| Исход | Действие |
| --- | --- |
| `refuse` | Заходящему игроку отказывают с сообщением `pipeline.policy.taken`; держатель сохраняет ник. |
| `rename-arriving` | Держатель сохраняет ник; аккаунт заходящего игрока получает новый. |
| `rename-holder` | Аккаунт заходящего игрока получает ник; держатель получает новый. |

Аддоны и провайдеры могут добавлять собственные исходы; их id появляются в `outcomes`. Правило, называющее несуществующий исход, выводится в консоль как ошибка при запуске и перезагрузке и вместо этого отказывает заходящему игроку.

```yaml
outcome:
  id: rename-holder
  with:
    holderOnline: KICK_HOLDER
```

</Setting>

### outcomes и providers [#outcomes-and-providers]

Настройки исхода берутся из трёх мест, и каждое указывает только то, что меняет:

1. `with` правила — оно побеждает;
2. `providers.<provider>.<outcome>` — для провайдера аккаунта, который исход переименовывает: держателя для `rename-holder`, заходящего игрока для остальных;
3. `outcomes.<outcome>` — Identica записывает туда значения исхода по умолчанию.

```yaml
providers:
  credential:
    rename-holder:
      pattern: "{username}_offline"
```

<Setting
  name="pattern"
  depth={4}
  takes="строку"
  default='`"{username}_{provider}"`'
  affects="новый ник у `rename-holder` и `rename-arriving`"
>

`{username}` — переименовываемый ник, `{provider}` — id провайдера переименовываемого аккаунта. Символы, которые Minecraft не допускает в нике, то есть всё, кроме букв, цифр и `_`, отбрасываются.

</Setting>

<Setting
  name="tooLong"
  depth={4}
  takes="`SHORTEN` или `REFUSE`"
  default="`SHORTEN`"
  affects="что происходит, если новый ник длиннее 16 символов, допустимых в Minecraft"
>

`SHORTEN` укорачивает исходный ник, пока результат не поместится: `Christopherson` становится `Chris_credential`. `REFUSE` вместо этого отказывает заходящему игроку, и держатель сохраняет ник.

</Setting>

<Setting
  name="taken"
  depth={4}
  takes="`NUMBER` или `REFUSE`"
  default="`NUMBER`"
  affects="что происходит, если новым ником уже владеет другой аккаунт"
>

`NUMBER` добавляет число от 2 до 9, например `Steve_credential2`, и отказывает заходящему игроку, если заняты все. `REFUSE` отказывает сразу.

</Setting>

<Setting
  name="holderOnline"
  depth={4}
  takes="`KEEP_PLAYING` или `KICK_HOLDER`"
  default="`KEEP_PLAYING`"
  affects="что делает `rename-holder` с держателем, который сейчас в сети"
>

С `KEEP_PLAYING` держатель играет под ником, пока не выйдет, и со следующего входа играет под новым. Оба сохранённых ника меняются сразу, поэтому заходящий игрок в этой сессии играет под ником, составленным по тем же настройкам `rename-holder`, например `Steve_premium`, а под самим ником — со следующего входа, когда держатель уже вышел.

С `KICK_HOLDER` держателя отключают с сообщением `pipeline.policy.holderReplaced`, и с этого момента ник свободен. Прокси называет заходящего игрока, пока держатель ещё подключён, поэтому и здесь заходящий игрок проводит первую сессию под ником, составленным по этим настройкам.

</Setting>

#### Ники без правила [#names-made-without-a-rule]

Identica использует настройки `rename-holder` в двух случаях, которые не решает ни одно правило:

- Два аккаунта одного провайдера с `OWNED_USERNAME` хотят один ник, значит, ник держателя устарел: провайдер переименовал держателя, а тот с тех пор не заходил. Ник получает его нынешний владелец, а держатель — ник по настройкам `rename-holder` для своего провайдера. При следующем входе держателя новый ник от провайдера проходит через правила как `PROVIDER_RENAME`.
- На этом прокси под ником аккаунта ещё играет другой игрок, например держатель, которого переименовали, пока он был в сети, и который ещё не вышел. Тогда игрок в этой сессии играет под ником по настройкам `rename-holder` для своего провайдера.

## messages.yml

Сообщения применяются во всех сценариях.

<Setting
  name="pipeline.identity.synchronizationFailed"
  takes="список строк"
  affects="сообщение, которое показывается, когда Identica не удаётся обновить ник аккаунта"
>

</Setting>

<Setting
  name="pipeline.policy.taken"
  takes="список строк"
  affects="сообщение, с которым игроку отказывают, когда так решают правила конфликтов"
>

`{username}` — ник, который хотел игрок.

</Setting>

<Setting
  name="pipeline.policy.holderReplaced"
  takes="список строк"
  affects="сообщение, с которым отключают держателя в сети при `holderOnline: KICK_HOLDER`"
>

`{username}` — ник, который держатель потерял, `{renamed}` — ник, под которым он играет со следующего входа.

</Setting>

```yaml
pipeline:
  policy:
    taken:
      - "<red>{username} is taken, please join with another name.</red>"
    holderReplaced:
      - "<yellow>The owner of {username} has joined. Join again to play as {renamed}.</yellow>"
```
