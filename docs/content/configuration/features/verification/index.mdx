Verification adds a second step that can be required after a provider already identifies the player.
In practice, this means a player first authenticates with a provider and then confirms an additional verification method before the flow can continue.
Verification methods can come from built-in functionality or from installed addons.

## Verification in practice

A player joins through the `credential` provider and enters their password successfully.
Instead of finishing login immediately, Identica asks for a code from the built-in default TOTP verification method.
The player enters the current code from their authenticator app, verification succeeds, and only then does the login flow complete.

Each authenticator code is accepted once per account, whether it confirms a login, an enrollment or a protected action such as disabling the method: a code from the same time window, or an older one, is refused afterwards, even through another proxy of the network, and the player waits for the next code. A refused code gets the same answer as a wrong one. Recovery codes are single-use as well.

If verification is optional instead of required, the same provider can still work without forcing that second step for every player or every situation.

Verification is compiled into Identica. Shared defaults live under `features/verification/`; providers override them in `providers[].features.verification`. See [Settings](./settings/index.mdx).
