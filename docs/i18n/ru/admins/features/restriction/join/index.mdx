Ограничение входа позволяет персоналу на время закрыть провайдер для новых входов, например во время атаки ботов на регистрацию через Credential. Пока провайдер ограничен, проходят только игроки, у которых есть один из разрешённых провайдером сигналов; все остальные получают отказ с сообщением `denied`.

## Разрешите ограничивать провайдер [#allowing-a-provider-to-be-restricted]

Провайдер можно ограничить, только если для него включено ограничение входа. По умолчанию оно выключено. Включите его для провайдера в `providers/providers.yml` и выберите, кто всё равно сможет войти:

```yaml
providers:
  - id: "credential"
    features:
      restriction:
        join:
          enabled: true
          allow:
            - linked
            - recognized
```

Сигналы:

- `linked`: у игрока уже есть аккаунт у этого провайдера.
- `recognized`: игрок [распознан](../../recognition/index.mdx). Для провайдера должно быть включено распознавание; указание сигнала его не включает.

Пустой список `allow` не пропускает никого, пока провайдер ограничен. `enabled` и `allow` в `features/restriction/join/settings` — значения по умолчанию для всех провайдеров.

## Ограничение провайдера [#restricting-a-provider]

| Команда | Что делает |
| --- | --- |
| `/identica admin provider restriction join enable <provider>` | ограничивает провайдер |
| `/identica admin provider restriction join disable <provider>` | снимает ограничение |
| `/identica admin provider restriction join status [provider]` | показывает, какие провайдеры ограничены |

Для всех трёх нужно право `identica.admin.provider.restriction`. Команды и их сообщения находятся в `features/restriction/join/`.

## Что видит игрок, получивший отказ [#what-a-refused-player-sees]

Если Identica уже знает провайдера игрока, когда он заходит, прокси отклоняет подключение во время входа, до любого запроса. Игрок, чей провайдер выбирается только позже, получает отказ, когда завершается его регистрация или вход. После снятия ограничения игрок, получивший отказ, проходит при следующей попытке.

Игрок, который уже был в процессе входа, когда ограничение началось, тоже получает отказ, когда возвращается. `resumeBypass.authentication` и `resumeBypass.registration` в `features/restriction/join/settings` позволяют таким входам завершиться; новые попытки они никогда не пропускают, а сценарий должен разрешать продолжение через `allowResume`.

Все настройки описаны на странице [Настройки ограничения входа](../../../../configuration/features/restriction/join/index.mdx).
