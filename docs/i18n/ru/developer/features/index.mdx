Identica компилирует реализации своих функций прямо в плагин. Модули исходного кода разделяют зону ответственности, а поведение функций администраторы выбирают через глобальную конфигурацию и конфигурацию отдельных провайдеров.

## Гарантии провайдеров [#provider-guarantees]

`IdenticaProvider.guarantees()` возвращает `Set<ProviderGuarantee>`. Гарантия выражает то, что реализация гарантирует о своих идентичностях. Это не переключатель для администратора, и правила конфликтов ников сопоставляются именно с гарантиями.

`ProviderGuarantee.OWNED_USERNAME` означает, что провайдер владеет никами своих игроков: двое его игроков не могут одновременно владеть одним ником, и он проверяет, что игрок владеет ником, с которым заходит. Identica следует этому нику для аккаунта, чьей основной привязкой является провайдер, если только администратор не назначил ник вручную. Провайдер Premium объявляет эту гарантию, провайдер Credential — нет. Конфигурация провайдера не может выдать гарантию.

Работа с никами — это поведение ядра, а не функция, и она никогда не указывается в `supportedFeatures()`. Её контракты находятся в `identica-api`: `UsernameAssigner` в `me.whereareiam.identica.identity.username`, модели в `me.whereareiam.identica.model.identity.username`, закрытые типы в `me.whereareiam.identica.type.identity.username`, `UsernameChangedEvent` в `me.whereareiam.identica.event.identity` и сервисы хранения данных в `me.whereareiam.identica.persistence.username`. Сопоставление правил и документы ников находятся в `identica-common`, фазы обработки ников — в `identica-engine`, а таблицы ников — в `identica-adapter-database/database-common`. См. [Ник](../../configuration/identity/username/index.mdx).

### Исходы конфликтов [#conflict-outcomes]

Конфликты двух аккаунтов за то, что может быть только у одного из них, проходят через `ConflictService` в `me.whereareiam.identica.conflict`. Каждый вид конфликта, например `UsernameConflict.KIND`, хранит свои правила в собственном документе; сервис находит самое конкретное подходящее правило и исход, который оно называет. Исходы регистрируются по id вместе с настройками, поэтому аддон или провайдер может добавить свой — через `ConflictService.register` или вернув его из `IdenticaProvider.conflictOutcomes()`, тогда он зарегистрирован, пока провайдер включён. Исход решает только, что остаётся у каждой стороны; ни один не пускает игрока в чужой аккаунт.

```java
public final class LongestPlaytimeOutcome implements ConflictOutcome<UsernameConflict, UsernameConflictDecision, LongestPlaytime> {
    @Override
    public ConflictKind<UsernameConflict, UsernameConflictDecision> kind() {
        return UsernameConflict.KIND;
    }

    @Override
    public String id() {
        return "longest-playtime";
    }

    @Override
    public Class<LongestPlaytime> settingsType() {
        return LongestPlaytime.class;
    }

    @Override
    public LongestPlaytime defaults() {
        return new LongestPlaytime();
    }

    @Override
    public UsernameConflictDecision decide(UsernameConflict conflict, LongestPlaytime settings) {
        return playtime.longer(conflict.getSituation())
                ? UsernameConflictDecision.renameHolder(settings.getHolderRename())
                : UsernameConflictDecision.renameArriving(settings.getRename());
    }
}
```

У исхода есть id в нижнем регистре через дефис, типизированная модель настроек и её значения по умолчанию. После регистрации Identica записывает значения по умолчанию в `outcomes.longest-playtime`; администратор меняет их там, в `providers.<провайдер>.longest-playtime` или в отдельном правиле, а правило называет исход как `outcome: longest-playtime`. `actsOn()` указывает, настройки провайдера какой стороны применяются.

## Поддерживаемые функции [#supported-features]

`IdenticaProvider.supportedFeatures()` возвращает идентификаторы функций, с которыми интегрируется провайдер. Поддержку объявляет разработчик провайдера, а включение выбирает администратор. Объявление поддержки не активирует функцию и не переопределяет конфигурацию.

```java
@Override
public Set<ProviderGuarantee> guarantees() {
    return Set.of(ProviderGuarantee.OWNED_USERNAME);
}

@Override
public Set<String> supportedFeatures() {
    return Set.of("recognition", "verification", "restriction", "restriction-join");
}
```

Провайдеры предоставляют конструктор без аргументов, чтобы загрузчик мог проверить их объявления до внедрения зависимостей. Объявления не должны полагаться на внедряемые сервисы. Объявление неизвестной функции не даёт провайдеру загрузиться. Явное включение известной функции, которую провайдер не поддерживает, тоже приводит к ошибке загрузки провайдера.

## Конфигурация [#configuration]

Каждая функция хранит свои настройки в `features/<id>/`; ограничение входа использует `features/restriction/join/`. Переопределения для провайдера находятся в `providers[].features`. Незаданные значения наследуются из глобальных значений по умолчанию функции. Явное `enabled: false` у провайдера отключает функцию для этого провайдера, а `enabled: true` может переопределить глобальное значение по умолчанию false.

`FeatureRegistry.isEnabled(providerId, featureId)` учитывает и объявленную поддержку, и действующую политику включения. `isAvailable(featureId)` описывает только то, скомпилирована ли функция, и не проверяет, включил ли её администратор. Интеграции провайдеров должны использовать первый метод, когда решают, выполнять ли необязательное поведение.

Глобальная политика верификации для провайдеров задаётся в `defaults` в `features/verification/settings`. Распознавание и Sentinel используют значение `enabled` в своих настройках. У ограничения есть собственное значение `enabled` по умолчанию; ограничение входа добавляет `enabled` и `allow` в `features/restriction/join/settings`. Отключение охватывающего переключателя `features.restriction.enabled` отключает для этого провайдера и ограничение входа.

Защищённые действия проверяют верификацию для провайдера текущей сессии. Настройки целевого провайдера не должны позволять обойти политику верификации исходной сессии.

Функция сама обновляет свои документы собственным потоком миграций Strata `identica/feature/<id>/config`: `ConfiguraTarget` на папке данных, который хранит версию в `settings` функции, и пронумерованные миграции. Модуль функции добавляет поток в набор `MigrationStream<ConfigContext>`, например методом с `@ProvidesIntoSet`, и до чтения любого документа Identica за один запуск Strata выполняет поток ядра, а затем потоки всех функций. Значение, которое функция забирает из документа ядра, например `connection.sentinels` из настроек 2.2.1, переносит и удаляет миграция функции; ядро такие разделы не трогает. Пишите переносы так, чтобы они заполняли только пустые места и ничего не делали, если значения уже нет: миграция определяет, что делать, по имеющимся разделам.

## Ответственность за реализацию [#implementation-ownership]

`identica-feature` явно собирает встроенные реализации через `BuiltinFeatures`. Нет ни сканера каталога функций, ни отдельной установки функций, ни выбора функций во время сборки. jar-файлы модулей функций — это зависимости сборки, которые компилируются в итоговый плагин.

`IdenticaFeature` отвечает за общие модули, инициализацию, завершение работы и необязательные вклады на уровне отдельных провайдеров. Внутренние объявления зависимостей определяют порядок связывания. `configurationPath()` указывает поддерево настроек провайдера, а `enabledByDefault(context)` читает общее значение по умолчанию, которым владеет функция. Глобальные сервисы инициализируются один раз; провайдеры добавляют только свои интеграции.

Держите слушатели, команды, расширения конвейера, модели, хранение данных и конфигурацию в той подсистеме, которая ими владеет. Регистрируйте ресурсы жизненного цикла при инициализации и удаляйте их при завершении работы, в том числе после частично неудавшейся инициализации. Обязательные подсистемы используют `RuntimeLifecycle` и указывают `StartupPhase`, в которой запускаются; в реестре функций они не появляются. Identica запускает фазы по порядку и останавливает их в обратном, а создание жизненного цикла не выполняет ввода-вывода: документы, база данных и другие хранилища читаются, когда он запускается.

## Проверка [#validation]

Тестируйте поведение гарантий без флагов функций, поддержку — отдельно от включения, явно заданные значения false, унаследованные глобальные значения и разные настройки у разных провайдеров. Тестируйте очистку жизненного цикла и проверяйте, что общая конфигурация провайдера сохраняет настройки, не относящиеся к изменяемой функции.
