## detection

`detection` определяет, кого из заходящих игроков Premium считает владельцем лицензионного аккаунта с их ником.
Игрока, которого Premium считает лицензионным, просят выполнить вход через лицензионный аккаунт: в режиме прохождения `SEAMLESS` — сразу при рукопожатии, в режиме `INTERACTIVE` — когда он выбирает Premium, — а предлагается Premium только таким игрокам.
Все остальные игроки переходят к следующему провайдеру, например Credential.

Ники, уже связанные с аккаунтом, подчиняются этому аккаунту. Ник, связанный с Premium, всегда требует входа через лицензионный аккаунт, а ник, связанный с другим провайдером, — нет.

```yaml
detection:
  methods:
    - CLIENT_PROFILE
    - LOOKUP
  recheckOnMismatch: false
  lookup:
    profileEndpoint: "https://api.mojang.com/users/profiles/minecraft/%s"
    timeout: "3s"
    cacheTtl: "5m"
```

### methods

- Принимает: список из `CLIENT_PROFILE` и `LOOKUP`
- По умолчанию: `["LOOKUP"]`
- Влияет на: как игрок с непривязанным ником распознаётся как лицензионный

Premium перебирает методы сверху вниз. Метод либо решает, лицензионный игрок или нет, либо передаёт его следующему методу.
Игрок, о котором не принял решения ни один метод, считается нелицензионным.

- `LOOKUP` считает лицензионным каждый ник, у которого есть лицензионный профиль. Этот метод всегда принимает решение, поэтому методы после него никогда не проверяются, и в таком случае Premium пишет предупреждение в лог при запуске.
- `CLIENT_PROFILE` <Badge type="warning">Экспериментально</Badge> сравнивает идентификатор профиля, который клиент отправляет в начале входа, с лицензионным профилем его ника. Официальный лаунчер отправляет идентификатор аккаунта, в который он вошёл, а пиратские (офлайн) лаунчеры — другой. Совпадение означает лицензионного игрока, другой идентификатор — нелицензионного. Клиенты старше 1.19.1 не отправляют идентификатор и передаются следующему методу.

| `methods` | Клиент 1.19.1 или новее | Более старый клиент |
|---|---|---|
| `["LOOKUP"]` | Ник лицензионного аккаунта: просят войти через лицензионный аккаунт | То же |
| `["CLIENT_PROFILE", "LOOKUP"]` | Просят войти через лицензионный аккаунт, только если клиент отправляет лицензионный профиль | Ник лицензионного аккаунта: просят войти через лицензионный аккаунт |
| `["CLIENT_PROFILE"]` | Просят войти через лицензионный аккаунт, только если клиент отправляет лицензионный профиль | Считается нелицензионным |

Если указан только `LOOKUP`, офлайн-игрока с ником лицензионного аккаунта при первом входе просят войти через лицензионный аккаунт. Его клиент не может этого сделать и отключается с сообщением о недействительной сессии; следующий вход с того же IP в течение [`attemptTtl`](../../../../../configuration/providers/index.mdx#attempttl) переходит к следующему провайдеру, если только ник за это время не привязали к Premium.
С `CLIENT_PROFILE` такой игрок переходит к следующему провайдеру уже при первом входе, а в режиме прохождения `INTERACTIVE` Premium ему не предлагается.

`CLIENT_PROFILE` также защищает ники, привязанные к Premium. Клиенту, который отправляет идентификатор профиля, отличный от привязанного, отказывают во входе с сообщением `verification.ownedUsername` из `messages.yml` провайдера Premium — если только ник теперь не принадлежит профилю, который отправил этот клиент.

Клиент отправляет идентификатор профиля сам, поэтому `CLIENT_PROFILE` решает только одно: просить ли вход через лицензионный аккаунт. Сам вход через лицензионный аккаунт по-прежнему проверяет аккаунт через Mojang.

Velocity сообщает идентификатор профиля через свой API. BungeeCord хранит его в запросе на вход, но не предоставляет к нему доступа, поэтому Identica читает его из класса подключения BungeeCord; в сборке BungeeCord без него каждый клиент считается клиентом старше 1.19.1.

### recheckOnMismatch

- Принимает: `true` или `false`
- По умолчанию в шаблоне: `false`
- Влияет на: что делает `CLIENT_PROFILE`, если идентификатор профиля клиента отличается от найденного профиля

Если параметр включён, при несовпадении профиль запрашивается повторно в обход кэша, прежде чем игрок будет признан нелицензионным.
Это учитывает ник, который в течение `lookup.cacheTtl` перешёл к другому лицензионному аккаунту, ценой одного дополнительного запроса для каждого офлайн-игрока с ником лицензионного аккаунта.

### lookup

`lookup` определяет, как Premium ищет лицензионный профиль ника. Его используют оба метода определения и выбор провайдера в режиме прохождения `INTERACTIVE`.

#### profileEndpoint

<Badge type="warning">Для опытных</Badge>

- Принимает: строку-шаблон URL
- По умолчанию в шаблоне: `"https://api.mojang.com/users/profiles/minecraft/%s"`
- Влияет на: HTTP-адрес, по которому лицензионный профиль ищется по нику

В качестве плейсхолдера поддерживается либо `%s`, либо `{username}`.
Перед подстановкой ник кодируется для URL.
Адрес отвечает профилем в формате JSON, где идентификатор находится в поле `id`, либо кодом `204` или `404`, если у ника нет профиля.

Если значение пустое, считается, что ни у одного ника нет лицензионного профиля.

#### timeout

<Badge type="warning">Для опытных</Badge>

- Принимает: положительную длительность
- По умолчанию в шаблоне: `"3s"`
- Влияет на: тайм-аут HTTP-запроса при поиске профиля и общее время ожидания проверки права на вход через лицензионный аккаунт

Если значение нулевое или отрицательное, построитель HTTP-запросов перестаёт задавать явный тайм-аут запроса.
Обработчик проверки права тоже добавляет свой тайм-аут завершения, только если значение положительное.

Если поиск завершился ошибкой или по тайм-ауту, считается, что у ника нет лицензионного профиля, и такой ответ не кэшируется.

#### cacheTtl

- Принимает: неотрицательную длительность
- По умолчанию в шаблоне: `"5m"`
- Влияет на: сколько ответы на поиск хранятся в реплицируемом кэше профилей

Если значение нулевое или отрицательное, кэш не используется, и каждый запрос уходит прямо на настроенный адрес.

## profileSnapshotTtl

- Принимает: неотрицательную длительность
- По умолчанию в шаблоне: `"10m"`
- Влияет на: сколько замеченные снимки лицензионных профилей хранятся в кэше по нику

Хранилище профилей Premium сохраняет снимки идентификаторов профилей в пространстве имён реплицируемого кэша и очищает их при изменениях жизненного цикла аккаунта.
Если значение нулевое или отрицательное, снимки вообще не записываются.

## replication.cache

<Badge type="warning">Для опытных</Badge>

Провайдер Premium использует собственные пространства имён реплицируемого кэша для двух разных целей.

### profile

- Принимает: строку — пространство имён
- По умолчанию в шаблоне: `"premium-profile"`
- Влияет на: пространство имён реплицируемого кэша для ответов на поиск профилей

Если значение пустое, инициализация кэша поиска лицензионных профилей завершается ошибкой.

### profileSnapshot

- Принимает: строку — пространство имён
- По умолчанию в шаблоне: `"premium-profile-snapshot"`
- Влияет на: пространство имён реплицируемого кэша для сохранённых снимков лицензионных профилей

Если значение пустое, инициализация хранилища снимков лицензионных профилей завершается ошибкой.
