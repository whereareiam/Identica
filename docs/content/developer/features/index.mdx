title: Provider traits and features
description: Identity guarantees, supported integrations, and operator-controlled feature policies.

Identica compiles its feature implementations into the plugin. Source modules separate ownership; operators choose feature behavior through global and per-provider configuration.

## Provider traits

`IdenticaProvider.traits()` returns `Set<ProviderTrait>`. A trait states an identity guarantee supplied by the implementation. It is not an operator toggle.

`ProviderTrait.AUTHORITATIVE_USERNAME` means Identica follows the provider's verified username for its primary account link, subject to manual authority and conflict policy. Premium declares this trait. Credential does not. Provider configuration cannot grant the trait.

Username handling is core behavior, not a feature, and is never listed in `supportedFeatures()`. Its contracts are in `identica-api`: `UsernameConflictHandler` in `me.whereareiam.identica.identity.username`, the models in `me.whereareiam.identica.model.identity.username`, `UsernameChangedEvent` in `me.whereareiam.identica.event.identity`, and the persistence services in `me.whereareiam.identica.persistence.username`. Conflict detection and the username documents are in `identica-common`, the username phases are in `identica-engine`, and the username tables are in `identica-adapter-database/database-common`. See [Username authority](../../configuration/identity/username/index.mdx).

## Supported features

`IdenticaProvider.supportedFeatures()` returns the feature IDs the provider integrates with. Support is declared by the provider developer; enablement is chosen by the operator. Declaring support does not activate the feature or override configuration.

```java
@Override
public Set<ProviderTrait> traits() {
    return Set.of(ProviderTrait.AUTHORITATIVE_USERNAME);
}

@Override
public Set<String> supportedFeatures() {
    return Set.of("recognition", "verification", "restriction", "restriction-join");
}
```

Providers expose a no-argument constructor so the loader can inspect their declarations before injection. Declarations must not rely on injected services. Declaring an unknown feature prevents that provider from loading. Explicitly enabling a known feature that the provider does not support also produces a provider loading error.

## Configuration

Each feature owns its settings under `features/<id>/`; join restriction uses `features/restriction/join/`. Provider overrides live under `providers[].features`. Omitted values inherit the feature's global defaults. An explicit provider `enabled: false` disables that feature for that provider, while `enabled: true` can override a global default of false.

`FeatureRegistry.isEnabled(providerId, featureId)` combines declared support and the effective enable policy. `isAvailable(featureId)` only describes compiled availability and is not a check for operator enablement. Provider integrations must use the former when deciding whether to execute optional behavior.

Verification's global provider policy is `defaults` in `features/verification/settings`. Recognition and sentinel use their settings' `enabled` value. Restriction has its own `enabled` default; join restriction adds `enabled` and `allow` in `features/restriction/join/settings`. Disabling the enclosing `features.restriction.enabled` switch also disables join restriction for that provider.

Protected actions evaluate verification for the current session's provider. A target provider's settings must not bypass the source session's verification policy.

A feature upgrades its own documents with a Strata migration stream of its own, `identica/feature/<id>/config`: a `ConfiguraTarget` on the data directory that keeps its version in the feature's `settings`, and its numbered migrations. Its module adds the stream to the set of `MigrationStream<ConfigContext>`, for example with a `@ProvidesIntoSet` method, and Identica runs the core's stream and then every feature's in one Strata run before any document is read. A value a feature takes over from a core document, such as `connection.sentinels` of 2.2.1's settings, is moved and removed by the feature's migration; the core leaves those sections alone. Write the moves so that they only fill empty places and do nothing when the value is gone: a migration finds what to do by the sections that are there.

## Implementation ownership

`identica-feature` composes the built-in implementations explicitly through `BuiltinFeatures`. There is no feature directory scanner, separate feature installation, or build-time feature selector. Feature module jars are build dependencies compiled into the final plugin.

`IdenticaFeature` owns shared modules, initialization, shutdown, and optional provider-local contributions. Its internal dependency declarations determine wiring order. `configurationPath()` identifies the provider settings subtree, and `enabledByDefault(context)` reads the feature-owned shared default. Global services are initialized once; providers contribute only their integrations.

Keep listeners, commands, pipeline extensions, models, persistence and configuration with the subsystem that owns them. Register lifecycle resources during initialization and remove them during shutdown, including partial initialization failures. Mandatory subsystems use `RuntimeLifecycle` and name the `StartupPhase` they start in; they do not appear in the feature registry. Identica starts the phases in order and stops them in reverse, and building a lifecycle does no I/O: documents, the database and other stores are read once it starts.

## Validation

Test trait behavior without feature flags, support separately from enablement, explicit false values, inherited global values, and different settings on different providers. Test lifecycle cleanup and verify that shared provider configuration retains unrelated feature settings.
