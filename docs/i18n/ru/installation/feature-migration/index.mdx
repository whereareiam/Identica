Эта миграция нужна установкам, в которых общая конфигурация хранится в `providers/capabilities`, а переопределения для провайдеров — в `providers[].capabilities`. Текущая структура описана в обычном справочнике по конфигурации.

Остановите прокси, прежде чем заменять основной jar-файл и jar-файлы провайдеров и переносить конфигурацию. При переносе перечисленных ниже папок сохраняйте существующие значения конфигурации и расширения файлов:

| Прежняя папка | Текущая папка |
| --- | --- |
| `providers/capabilities/recognition/` | `features/recognition/` |
| `providers/capabilities/restriction/` | `features/restriction/` |
| `providers/capabilities/restriction/join/` | `features/restriction/join/` |
| `providers/capabilities/authoritative-username/` | `identity/username/` |

При переносе всей папки restriction вместе с ней переносятся и вложенные документы join. Если в папке назначения уже есть файлы, объединяйте их вручную и внимательно, чтобы не потерять изменённые значения. Документы верификации размещаются в `features/verification/`. Политики Sentinel, его сообщения и пространство имён его кэша относятся к функции sentinel.

Перенесите изменённые поля sentinel из ядра, сохранив их значения:

| Прежний документ и поле | Текущий документ и поле |
| --- | --- |
| `settings`: `sentinels` | `features/sentinel/settings`: `sentinels` |
| `messages`: `engine.resumeSentineled` | `features/sentinel/messages`: `resumeSpam.denied` |
| `replication`: `cache.sentinels` | `features/sentinel/settings`: `replication.state` |

Если эти значения уже заданы в документах функции sentinel, сохраните их, а устаревшие поля ядра удалите. Чтобы защита работала, выберите `sentinel` при запуске.

В `providers/providers` перенесите `providers[].capabilities.recognition` в `providers[].features.recognition`, а `providers[].capabilities.restriction.join` — в `providers[].features.restriction.join`. Объедините их с существующим объектом `features`, сохранив `features.verification` и другие переопределения функций. После переноса настроек удалите устаревшее поддерево конфигурации `capabilities`.

Например, переопределение ограничения входа становится таким:

```yaml
providers:
  - id: premium
    features:
      restriction:
        join:
          enabled: true
          allow:
            - linked
            - recognized
```

Перенесите изменённые политики продолжения для ограничения входа из `engine`:

| Прежнее поле в `engine` | Текущее поле в `features/restriction/join/settings` |
| --- | --- |
| `scenarios.authentication.allowProviderRestrictionResumeBypass` | `resumeBypass.authentication` |
| `scenarios.registration.allowProviderRestrictionResumeBypass` | `resumeBypass.registration` |

По умолчанию обе настройки функции равны `false`. Сохраните изменённые значения для аутентификации и регистрации, а затем удалите старые поля engine. Поле `scenarios.migration.allowProviderRestrictionResumeBypass` удалите, ничем его не заменяя: этот флаг не использовался. Возможность продолжить сценарий в принципе по-прежнему определяет параметр `allowResume` в engine.

Значения по умолчанию для конфликтов ников находятся в `identity/username/conflicts`. Перенесите туда нужную конфигурацию `rules.username`, сохранив карту `rules` верхнего уровня и текущее содержимое правил. Документ ядра `providers/conflicts` остаётся необязательным общим переопределением: любая запись `rules.username`, оставленная в нём, имеет приоритет над правилами функции. Если конфликтами ников должен управлять документ функции, удалите эту запись из документа ядра; остальные ключи конфликтов сохраните.

Например, `identity/username/conflicts` может содержать:

```yaml
rules:
  username:
    default:
      resolvers:
        - id: format_display
          parameters:
            format:
              pattern: "{username}*"
            target: joiner
```

Поле документа называется `rules`, а не `conflicts`. Провайдер Premium объявляет у себя признак `AUTHORITATIVE_USERNAME`. Обработка ников следует этому признаку, и отдельного переключателя для её включения нет.

Сообщения, относящиеся только к никам, теперь находятся в `identity/username/messages`:

| Прежнее поле в `messages` ядра | Текущее поле сообщения функции |
| --- | --- |
| `scenarios.authentication.errors.identity.replicationMissing` | `pipeline.identity.synchronizationFailed` |
| `scenarios.registration.errors.identity.replicationMissing` | `pipeline.identity.synchronizationFailed` |
| `scenarios.migration.errors.identity.replicationMissing` | `pipeline.identity.synchronizationFailed` |
| `scenarios.authentication.conflictEntrypointRequired` | `pipeline.policy.entrypointRequired` |

Если старые значения для разных сценариев отличаются, выберите одно общее сообщение об ошибке синхронизации, сохраните уже изменённые сообщения функции и удалите устаревшие поля ядра. Текущая структура описана в разделе [Сообщения о никах](../../configuration/identity/username/index.mdx#messages).

Значения верификации по умолчанию применяются ко всем ID провайдеров, у которых явно задан узел `providers[].features.verification`. Провайдеры без этого узла через это поддерево конфигурации не участвуют. Проверьте переопределения для неофициальных провайдеров, учитывая, что к ним применяются те же значения по умолчанию, что и к официальным: верификация включена, `KEEP_LOCKED` и один включённый способ `totp` с приоритетом `100`.

Каждую поддерживаемую функцию можно настроить глобально и в `providers[].features`. Все реализации уже входят в сборку Identica.

## API провайдеров [#provider-api]

Провайдеры объявляют гарантии идентичности через `traits(): Set<ProviderTrait>`, а необязательные интеграции — через `supportedFeatures(): Set<String>`. Для ников, за которые отвечает провайдер, используется `ProviderTrait.AUTHORITATIVE_USERNAME`; удалите объявление функции `username`, если оно есть. Включение функций — это настройка администратора, и оно не может наделить провайдер признаками или поддержкой интеграции.

Переопределения верификации для провайдеров теперь наследуют `defaults` из `features/verification/settings`, в том числе когда узла переопределения нет вовсе. Если верификацию нужно отключить, явно укажите для провайдера `enabled: false`.
