На этой странице описаны настройки верификации, с помощью которых вы управляете её поведением.
Поведение по умолчанию также можно переопределить для провайдера в `providers[].features.verification`.

Общие настройки находятся в `features/verification/settings`, сообщения — в `features/verification/messages`. Настройки провайдера наследуют общую политику `defaults`.

## Настройки [#settings]

### challengeTtl

- Принимает: положительную длительность
- По умолчанию: `"2m"`
- Влияет на: как долго остаётся действительным ожидающий запрос верификации

Это время жизни (TTL) применяется к состоянию ожидающего запроса — например, когда игроку предложено ввести код TOTP или код восстановления.
Если значение слишком мало, игроки могут потерять запрос, не успев его пройти.
Если слишком велико, устаревшее состояние ожидающего запроса остаётся действительным дольше, чем нужно.

### enrollmentTtl

- Принимает: положительную длительность
- По умолчанию: `"10m"`
- Влияет на: как долго остаётся действительной незавершённая привязка метода верификации

Этот TTL применяется к состоянию привязки — например, когда игрок находится посреди настройки и подтверждения TOTP.

### autoSelectCurrentProvider

<Badge type="warning">Для опытных</Badge>

- Принимает: `true` или `false`
- По умолчанию: `true`
- Влияет на: выбирается ли только что привязанный метод автоматически для текущего провайдера, когда это возможно

Если настройка включена, Identica пытается автоматически выбрать для текущего провайдера метод, который игрок только что привязал.
Если в процессе привязки явно не указан идентификатор провайдера, Identica по возможности берёт провайдера из текущей сессии.

Это упрощает жизнь игроку после успешной привязки, но некоторые администраторы предпочитают требовать явного выбора метода.

### totp

Раздел `totp` настраивает встроенный метод верификации через приложение-аутентификатор.

#### displayName

- Принимает: строку
- По умолчанию: `"Authenticator App"`
- Влияет на: название встроенного метода TOTP, которое видят пользователи

Если значение пустое, описание встроенного метода использует `totp`.

#### issuer

- Принимает: строку
- По умолчанию: `"Identica"`
- Влияет на: значение издателя (issuer), встраиваемое в сгенерированный URI OTPAuth

Обычно именно его приложения-аутентификаторы показывают как название сервиса или издателя аккаунта после импорта QR-кода или URI OTPAuth.

#### labelFormat

- Принимает: строку
- По умолчанию: `"{player}@{providerId}"`
- Влияет на: как формируется метка аккаунта в URI OTPAuth

Текущий шаг настройки TOTP заменяет такие плейсхолдеры:

- `{player}` — на текущий ник
- `{providerId}` — на идентификатор текущего провайдера

От этого зависит, как запись выглядит в приложениях-аутентификаторах.

#### digits

<Badge type="warning">Для опытных</Badge>

- Принимает: целое число
- По умолчанию: `6`
- Влияет на: сколько цифр содержит каждый сгенерированный код TOTP

Значение используется и при генерации URI OTPAuth, и при последующей проверке кодов TOTP.

#### period

<Badge type="warning">Для опытных</Badge>

- Принимает: положительную длительность
- По умолчанию: `"30s"`
- Влияет на: период TOTP, используемый при генерации и проверке кодов

Внутри встроенный метод TOTP переводит это значение в секунды для генерации OTPAuth и проверки кодов.

#### allowedPastWindows

<Badge type="warning">Для опытных</Badge>

- Принимает: целое число
- По умолчанию: `1`
- Влияет на: сколько предыдущих временных окон TOTP принимается при проверке

Чем больше значение, тем терпимее проверка к расхождению часов и медленному вводу, но тем она и мягче.

#### allowedFutureWindows

<Badge type="warning">Для опытных</Badge>

- Принимает: целое число
- По умолчанию: `1`
- Влияет на: сколько будущих временных окон TOTP принимается при проверке

Большие значения помогают при расхождении часов, но и расширяют допустимое окно проверки.

При любых окнах каждый код принимается один раз: после того как код принят, коды его окна и более ранних окон для этого аккаунта отклоняются. Поэтому игрок, у которого часы приложения спешат и который ввёл код будущего окна, ждёт окна после него, прежде чем следующий код будет принят.

### recoveryCodes

Подраздел `recoveryCodes` управляет резервными кодами, которые генерируются при привязке TOTP.

#### enabled

- Принимает: `true` или `false`
- По умолчанию: `true`
- Влияет на: генерируются ли коды восстановления при привязке TOTP

Если настройка отключена, встроенный процесс привязки TOTP не создаёт кодов восстановления.

#### amount

<Badge type="warning">Для опытных</Badge>

- Принимает: целое число
- По умолчанию: `8`
- Влияет на: сколько кодов восстановления генерируется при привязке TOTP

#### length

<Badge type="warning">Для опытных</Badge>

- Принимает: целое число
- По умолчанию: `10`
- Влияет на: сколько символов содержит каждый код восстановления до разбиения на группы

#### groupSize

<Badge type="warning">Для опытных</Badge>

- Принимает: целое число
- По умолчанию: `4`
- Влияет на: как сгенерированные коды восстановления визуально разбиваются на группы

Эта настройка меняет только оформление сгенерированных кодов восстановления, а не то, создаются ли они.

## Переопределения для провайдеров [#provider-overrides]

Функция верификации добавляет в конфигурацию провайдеров поля верификации на уровне провайдера — через `providers[].features.verification`.

Политику для провайдеров задаёт общий объект `defaults` в `features/verification/settings`. Отсутствующие узлы провайдеров и пропущенные поля наследуют её; значения по умолчанию не копируются в переопределения провайдеров.

```yaml
defaults:
  enabled: true
  required: false
  unavailableSelectionPolicy: KEEP_LOCKED
  methods:
    - id: totp
      enabled: true
      priority: 100
```

Провайдер может переопределить только нужные ему поля. Явно пустой список `methods: []` не разрешает этому провайдеру ни одного метода.

### features.verification.enabled

- Принимает: `true` или `false`
- По умолчанию: наследует `defaults.enabled` (`true`)
- Влияет на: участвует ли этот провайдер в общей системе верификации

Если переопределения для провайдера нет, общие значения по умолчанию применяются к провайдерам, которые заявляют поддержку верификации.

### features.verification.required

- Принимает: `true` или `false`
- По умолчанию: `false`
- Влияет на: становится ли верификация для этого провайдера обязательной, а не опциональной

### features.verification.unavailableSelectionPolicy

- Принимает: `"CLEAR_SELECTION"` или `"KEEP_LOCKED"`
- По умолчанию: наследует `defaults.unavailableSelectionPolicy` (`KEEP_LOCKED`)
- Влияет на: что происходит, если выбранный метод верификации недоступен

### features.verification.methods

- Принимает: список записей методов
- Влияет на: какие методы верификации доступны этому провайдеру и в каком порядке

Для любого идентификатора провайдера с явно заданным узлом верификации по умолчанию используется одна включённая запись `totp` с приоритетом `100`.

Каждая запись метода поддерживает поля:

- `id`: идентификатор метода верификации, например `totp`
- `enabled`: можно ли использовать этот метод
- `priority`: порядок, если доступно несколько методов
- `required`: необязательное переопределение общего для провайдера `required` на уровне метода
- `unavailableSelectionPolicy`: необязательное переопределение общего для провайдера `unavailableSelectionPolicy` на уровне метода

Если в записи метода не заданы `required` или `unavailableSelectionPolicy`, текущий механизм разрешения использует настройки верификации на уровне провайдера.
