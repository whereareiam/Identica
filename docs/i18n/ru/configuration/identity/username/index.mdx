У каждого аккаунта один ник, и он следует за основным провайдером аккаунта: лицензионный аккаунт Premium играет под своим ником Mojang, аккаунт Credential — под ником, с которым игрок зарегистрировался. Это обязательное поведение идентичности, а не функция, которую можно выключить.

Провайдер сообщает Identica, что он гарантирует о никах. Провайдер с гарантией `OWNED_USERNAME` владеет никами своих игроков: двое его игроков не могут одновременно владеть одним ником, и он проверяет, что игрок владеет ником, с которым заходит. Premium объявляет эту гарантию, Credential — нет, потому что игроки Credential выбирают ники сами. Конфигурация не может выдать гарантию.

Правила находятся в `identity/username/conflicts`, сообщения — в `identity/username/messages`.

## Уникальные ники [#unique-usernames]

Ники уникальны без учёта регистра, как ники Minecraft: пока аккаунт владеет ником `Alice`, никакой другой аккаунт не получит `alice` или `ALICE`. Когда игрок хочет ник, которым владеет другой аккаунт, решают [правила конфликтов](#conflict-rules). Ни один исход не пускает игрока в чужой аккаунт: правило решает только, какой из двух аккаунтов сохранит ник, а какой получит новый, или отказывает входящему игроку.

В базе данных из времён, когда ники ещё не были уникальными, несколько аккаунтов могут делить один ник. При обновлении базы ник остаётся за самым старым аккаунтом; остальные по-прежнему входят через собственные привязки к провайдерам. При каждом запуске консоль предупреждает о каждом нике, которым владеют несколько аккаунтов, и называет эти аккаунты с их UUID, провайдерами и временем последнего входа:

```text
Duplicate usernames: steve is shared by steve (…, providers credential, last seen …), Steve (…, providers premium, last seen …). …
```

`/identica admin username duplicates` выводит те же аккаунты. Чтобы оставить ник одному аккаунту, переименуйте остальные командой [`/identica admin username rename`](#renaming-an-account-by-hand).

## Когда возникает конфликт [#when-a-conflict-comes-up]

Игрок хочет ник в двух ситуациях:

- `FIRST_JOIN`: игрок впервые заходит через провайдера и хочет его ник. Это новый аккаунт, а также аккаунт, который переходит к другому провайдеру, например командой `/premium`, и с этого момента берёт ник у него.
- `PROVIDER_RENAME`: провайдер известного аккаунта даёт ему новый ник, например после смены ника в Mojang.

Если нужным ником никто не владеет, аккаунт его получает. Если ником владеет другой аккаунт, конфликт решают правила. Заходящий игрок — это **входящая** сторона (`arriving`); аккаунт, который владеет ником, — **держатель** (`holder`), он стоит на своём основном провайдере.

Конфликт решается до того, как прокси назовёт игрока, поэтому переименованный игрок сразу играет под новым ником, а игрок, которому отказали, получает отказ раньше любого запроса.

## Правила по умолчанию [#default-rules]

Правила по умолчанию называют только гарантии, а не провайдеров, поэтому охватывают и провайдеров, добавленных позже:

| Провайдер входящего | Провайдер держателя | Триггер | Исход |
| --- | --- | --- | --- |
| `OWNED_USERNAME` | без гарантий | `FIRST_JOIN` | `rename-holder`: ник получает его настоящий владелец, держателя переименовывают |
| `OWNED_USERNAME` | без гарантий | `PROVIDER_RENAME` | `rename-arriving`: держатель выбрал ник первым и сохраняет его, переименованный игрок получает новый ник |
| без гарантий | любой | любой | `refuse`: игрок, который выбирает ник сам, не может занять чужой |
| любой | любой | любой | `refuse` |

Например, игрок Credential зарегистрировал ник `Steve`. Когда владелец лицензионного аккаунта `Steve` впервые заходит через Premium, он получает `Steve`, а аккаунт Credential становится `Steve_credential`. Игрок Credential по-прежнему входит с тем же ником в клиенте и тем же паролем и с этого момента играет как `Steve_credential`.

Лицензионный игрок, который заходит через [точку входа](../../providers/index.mdx#entrypoints) Premium, попадает под первое правило. Лицензионного игрока, который заходит без неё, может отправить к запросу пароля аккаунта Credential, потому что ник совпадает с этим аккаунтом; см. [Как выбирается провайдер](../../providers/index.mdx#how-a-provider-is-picked).

## Правила конфликтов [#conflict-rules]

`identity/username/conflicts` содержит настройки каждого исхода, необязательные изменения для провайдеров и правила:

<Tabs items={["YAML", "JSON"]}>
  <Tab value="YAML">
```yaml
outcomes:
  rename-holder:
    pattern: "{username}_{provider}"
    tooLong: SHORTEN
    taken: NUMBER
    holderOnline: KEEP_PLAYING
  rename-arriving:
    pattern: "{username}_{provider}"
    tooLong: SHORTEN
    taken: NUMBER
  refuse: {}
providers: {}
rules:
  - arriving: { guarantees: [OWNED_USERNAME] }
    holder: { guarantees: [] }
    trigger: FIRST_JOIN
    outcome: rename-holder
  - arriving: { guarantees: [OWNED_USERNAME] }
    holder: { guarantees: [] }
    trigger: PROVIDER_RENAME
    outcome: rename-arriving
  - arriving: { guarantees: [] }
    outcome: refuse
  - outcome: refuse
```
  </Tab>
  <Tab value="JSON">
```json
{
  "outcomes": {
    "rename-holder": { "pattern": "{username}_{provider}", "tooLong": "SHORTEN", "taken": "NUMBER", "holderOnline": "KEEP_PLAYING" },
    "rename-arriving": { "pattern": "{username}_{provider}", "tooLong": "SHORTEN", "taken": "NUMBER" },
    "refuse": {}
  },
  "providers": {},
  "rules": [
    { "arriving": { "guarantees": ["OWNED_USERNAME"] }, "holder": { "guarantees": [] }, "trigger": "FIRST_JOIN", "outcome": "rename-holder" },
    { "arriving": { "guarantees": ["OWNED_USERNAME"] }, "holder": { "guarantees": [] }, "trigger": "PROVIDER_RENAME", "outcome": "rename-arriving" },
    { "arriving": { "guarantees": [] }, "outcome": "refuse" },
    { "outcome": "refuse" }
  ]
}
```
  </Tab>
</Tabs>

Правило без условий — наименее конкретное: оно решает всё, что не решает ни одно другое правило.

### Какое правило применяется [#which-rule-applies]

Из правил, подходящих к конфликту, побеждает самое конкретное:

1. правило, называющее id провайдеров для большего числа сторон, сильнее правила, называющего их для меньшего;
2. затем правило, называющее гарантии для большего числа сторон, сильнее правила, называющего их для меньшего;
3. затем правило, которое дополнительно задаёт `trigger` или `arrivedVia`, сильнее правила без них.

Из одинаково конкретных правил побеждает первое в списке. Если два одинаково конкретных правила могут подойти к одному конфликту, но решают его по-разному, консоль предупреждает об этом при запуске и перезагрузке, потому что второе там никогда не применится. Если не подходит ни одно правило, входящему игроку отказывают.

### rules[].arriving и rules[].holder [#rulesarriving-and-rulesholder]

Что правило требует от каждой стороны. Не указывайте сторону, чтобы принять любую.

#### guarantees

- Принимает: список гарантий, например `[OWNED_USERNAME]`
- Влияет на: на каких провайдерах может стоять сторона

Провайдер должен объявлять ровно эти гарантии: `[]` требует провайдера без гарантий, например Credential. Не указывайте поле, чтобы принять любого провайдера.

#### providers

- Принимает: список id провайдеров, например `[premium]`
- Влияет на: на каких провайдерах может стоять сторона

Id провайдеров сравниваются без учёта регистра. Правило с провайдерами конкретнее правила с гарантиями, поэтому так можно обработать одну пару провайдеров иначе, чем говорят правила по умолчанию.

### rules[].trigger

- Принимает: `FIRST_JOIN` или `PROVIDER_RENAME`
- Влияет на: к какой ситуации относится правило

Не указывайте, чтобы правило относилось к обеим.

### rules[].arrivedVia

- Принимает: причину, по которой был выбран провайдер входящего игрока, например `HOSTNAME`
- Влияет на: относится ли правило только к игрокам, попавшим к провайдеру таким путём

`HOSTNAME` означает, что игрок зашёл через одну из `entrypoints` провайдера. Не указывайте, чтобы принять любую причину.

### rules[].outcome

- Принимает: id исхода, например `rename-holder`, или `{ id: ..., with: { ... } }`, чтобы изменить часть его настроек только для этого правила
- Влияет на: как решается конфликт

| Исход | Действие |
| --- | --- |
| `refuse` | Входящему игроку отказывают с сообщением `pipeline.policy.taken`; держатель сохраняет ник. |
| `rename-arriving` | Держатель сохраняет ник; входящий аккаунт получает новый. |
| `rename-holder` | Входящий аккаунт получает ник; держатель получает новый. |

Аддон или провайдер может зарегистрировать собственные исходы; их id появляются в `outcomes`. Правило, называющее исход, который никто не зарегистрировал, выводится в консоль как ошибка при запуске и перезагрузке и вместо этого отказывает входящему игроку.

Например, это правило отключает держателя в сети, а все остальные правила сохраняют значения по умолчанию:

```yaml
outcome:
  id: rename-holder
  with:
    holderOnline: KICK_HOLDER
```

## Настройки исходов [#outcome-settings]

Настройки исхода берутся из трёх мест, и каждое указывает только то, что меняет:

1. `with` правила — оно побеждает;
2. `providers.<провайдер>.<исход>` — для провайдера аккаунта, на который действует исход: держателя для `rename-holder`, входящего аккаунта для остальных;
3. `outcomes.<исход>` — Identica записывает туда значения исхода по умолчанию, как только исход зарегистрирован.

Например, аккаунты Credential, теряющие ник, можно переименовывать иначе, чем остальные:

```yaml
providers:
  credential:
    rename-holder:
      pattern: "{username}_offline"
```

В документе по умолчанию для провайдеров ничего не меняется.

### pattern

- Принимает: строку
- По умолчанию: `"{username}_{provider}"`
- Влияет на: новый ник у `rename-holder` и `rename-arriving`

`{username}` — переименовываемый ник, `{provider}` — id провайдера переименовываемого аккаунта. Символы, которые Minecraft не допускает в нике, то есть всё, кроме букв, цифр и `_`, отбрасываются.

### tooLong

- Принимает: `SHORTEN` или `REFUSE`
- По умолчанию: `SHORTEN`
- Влияет на: что происходит, если новый ник длиннее 16 символов, допустимых в Minecraft

`SHORTEN` укорачивает исходный ник, пока результат не поместится: `Christopherson` становится `Chris_credential`. `REFUSE` вместо этого отказывает входящему игроку, и держатель сохраняет ник.

### taken

- Принимает: `NUMBER` или `REFUSE`
- По умолчанию: `NUMBER`
- Влияет на: что происходит, если новым ником уже владеет другой аккаунт

`NUMBER` добавляет число от 2 до 9, например `Steve_credential2`, и отказывает входящему игроку, если заняты все. `REFUSE` отказывает сразу.

### holderOnline

- Принимает: `KEEP_PLAYING` или `KICK_HOLDER`
- По умолчанию: `KEEP_PLAYING`
- Влияет на: что делает `rename-holder` с держателем, который сейчас в сети

С `KEEP_PLAYING` держатель играет под ником, пока не выйдет, и со следующего входа играет под новым. Оба сохранённых ника меняются сразу, поэтому входящий игрок в этой сессии играет под ником, составленным по тем же настройкам `rename-holder`, например `Steve_premium`, а под самим ником — со следующего входа, когда держатель уже вышел. С `KICK_HOLDER` держателя отключают с сообщением `pipeline.policy.holderReplaced`, и с этого момента ник свободен для всех. Прокси называет входящего игрока, пока держатель ещё подключён, поэтому и с этим исходом входящий игрок проводит первую сессию под ником, составленным по этим настройкам.

### Ники без правила [#names-made-without-a-rule]

Identica использует настройки `rename-holder` в двух случаях, которые не решает ни одно правило:

- Два аккаунта одного провайдера с `OWNED_USERNAME` хотят один ник, значит, ник держателя устарел: провайдер переименовал держателя, а тот с тех пор не заходил. Ник получает его нынешний владелец, а держатель — ник по настройкам `rename-holder` для своего провайдера. При следующем входе держателя новый ник от провайдера проходит через правила как `PROVIDER_RENAME`.
- На этом прокси под ником аккаунта ещё играет другой игрок, например держатель, которого переименовали, пока он был в сети, и который ещё не вышел. Тогда игрок в этой сессии играет под ником по настройкам `rename-holder` для своего провайдера.

## Неизменные правила [#fixed-rules]

Некоторые вещи не меняет ни одно правило:

- Ни один исход не пускает игрока в чужой аккаунт.
- Ник, назначенный администратором вручную, Identica никогда не меняет сама. Если правило переименовало бы такого держателя, вместо него переименовывается входящий аккаунт.
- Аккаунт, переименованный в конфликте, при следующем входе забирает свой ник обратно, как только им никто не владеет.
- Из аккаунтов, которые делят ник с тех времён, когда ники ещё не были уникальными, держателем считается тот, за кем ник остаётся для всех остальных; другие сохраняют свой ник, но держателями не считаются.

## Переименование аккаунта вручную [#renaming-an-account-by-hand]

`/identica admin username rename <аккаунт> <ник>` переименовывает аккаунт, указанный ником или UUID. Новый ник должен состоять из 3–16 букв, цифр или `_`, и никто не должен владеть им в любом регистре. Identica сохраняет такой ник: его не меняет ни конфликт, ни смена ника у провайдера. Игрок играет под ним со следующего входа.

## Сообщения [#messages]

Сообщения конвейера для ников находятся в `identity/username/messages` и применяются в сценариях аутентификации, регистрации и миграции.

### pipeline.identity.synchronizationFailed

- Принимает: список строк сообщения
- По умолчанию: встроенное сообщение об ошибке синхронизации ника
- Влияет на: сообщение, которое показывается, когда Identica не удаётся синхронизировать ник аккаунта

### pipeline.policy.taken

- Принимает: список строк сообщения
- По умолчанию: встроенное сообщение с занятым ником
- Влияет на: сообщение, с которым игроку отказывают, когда так решают правила конфликтов

Плейсхолдер `{username}` заменяется ником, который хотел игрок.

### pipeline.policy.holderReplaced

- Принимает: список строк сообщения
- По умолчанию: встроенное сообщение с обоими никами
- Влияет на: сообщение, с которым отключают держателя в сети при `holderOnline: KICK_HOLDER`

Плейсхолдер `{username}` — ник, который держатель потерял, `{renamed}` — ник, под которым он играет со следующего входа.

Например:

```yaml
pipeline:
  policy:
    taken:
      - "<red>{username} уже занят, зайдите с другим ником.</red>"
    holderReplaced:
      - "<yellow>Зашёл владелец ника {username}. Зайдите снова, чтобы играть как {renamed}.</yellow>"
```
