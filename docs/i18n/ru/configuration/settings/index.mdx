## Уровень логирования [#level]

`level` определяет, сколько Identica пишет в лог.

| Значение | Результат                                  |
|----------|--------------------------------------------|
| `0`      | только ошибки                              |
| `1`      | предупреждения и ошибки                    |
| `2`      | информация, предупреждения и ошибки        |
| `3`      | добавляется отладочный вывод (debug)       |
| `4`      | добавляется трассировка (trace)            |

<Tabs items={["YAML", "JSON"]}>
  <Tab value="YAML">
```yaml
level: 3
```
  </Tab>
  <Tab value="JSON">
```json
{
  "level": 3
}
```
  </Tab>
</Tabs>

В обычной работе используйте `2`, а `3` или `4` — когда отлаживаете маршрутизацию, конвейер или поведение провайдеров.

## identity

`identity` управляет назначением UUID аккаунтам и временем резервирования.

### uniqueIdMode

<Badge type="error">Опасно</Badge>

- Принимает: `"RANDOM"`, `"OFFLINE"` или `"PREMIUM"`
- По умолчанию: `"RANDOM"`
- Влияет на: то, как Identica назначает UUID впервые обнаруженным аккаунтам

<Tabs items={["RANDOM", "OFFLINE", "PREMIUM"]}>
  <Tab value="RANDOM">
    Создаёт для аккаунта новый случайный UUID, принадлежащий Identica.
    Он не выводится из ника в Minecraft и не пытается повторить соглашения об офлайн-UUID или UUID лицензионных аккаунтов и провайдеров.

    `RANDOM` — рекомендуемый режим.
    Это самый стабильный вариант в Identica: он генерирует собственный UUID Identica, который не зависит от соглашений Minecraft об офлайн- и онлайн-UUID.
    Благодаря этому смену провайдера и смену ника проще обработать внутри Identica, не теряя связь с аккаунтом.
  </Tab>
  <Tab value="OFFLINE">
    Выводит UUID из ника в офлайн-режиме по стандартной схеме `OfflinePlayer:<username>`.
    На практике это значит, что UUID всегда строится на основе офлайн-ника, а не метаданных провайдера.

    Пример: если игрок виден как `Steve`, Identica генерирует тот же UUID, что сгенерировал бы офлайн-сервер для `OfflinePlayer:Steve`.
    Если игрок позже сменит ник, основа офлайн-UUID сменится вместе с новым ником.
  </Tab>
  <Tab value="PREMIUM">
    Сначала пытается использовать UUID субъекта провайдера.
    Если он не подходит, Identica берёт наблюдаемый UUID лицензионного аккаунта, если такой есть и он не совпадает с офлайн-UUID для текущего ника.

    На практике порядок такой:

    1. использовать субъект провайдера, если он уже является корректным UUID
    2. иначе использовать UUID, полученный из запроса профиля на платформе, если он похож на настоящий UUID лицензионного аккаунта
    3. иначе в этом режиме UUID определить не удаётся
  </Tab>
</Tabs>

| Свойство | `RANDOM` | `OFFLINE` | `PREMIUM` |
| --- | --- | --- | --- |
| Рекомендуется по умолчанию | Да | Нет | Нет |
| Генерирует собственный UUID Identica | Да | Нет | Нет |
| Выводится из ника | Нет | Да | Нет |
| Использует UUID провайдера или лицензионного аккаунта | Нет | Нет | Да |
| Не меняется при смене ника внутри Identica | Да | Нет | Зависит от провайдера |
| Подходит для совместимости с офлайн-UUID | Нет | Да | Нет |
| Легко перейти на плагины, ожидающие стандартных соглашений Minecraft об UUID | Нет | Да | Зависит от целевого плагина и поведения провайдера |
| Может не сработать, если подходящего UUID лицензионного аккаунта нет | Нет | Нет | Да |

Для долгосрочной стабильности внутри Identica обычно лучше всего подходит `RANDOM`.
`OFFLINE` существует в основном для сценариев совместимости.
`PREMIUM` — самый строгий режим; он нужен в основном конфигурациям, которым явно требуется преемственность UUID лицензионного аккаунта или провайдера.

#### Выбор UUID для отдельного аккаунта [#choosing-the-uuid-of-one-account]

`uniqueIdMode` определяет UUID аккаунта при его создании, и аккаунт сохраняет этот UUID.
Чтобы выдать одному игроку другой UUID, например его офлайн-UUID в сети с `RANDOM`, зарезервируйте UUID за его ником и попросите игрока зарегистрироваться заново:

1. `/identica admin delete <username>` и `/identica admin delete confirm` удаляют текущий аккаунт. При удалении UUID аккаунта не сохраняется: без резервирования следующая регистрация получит новый UUID согласно `uniqueIdMode`.
2. `/identica admin reservation set <username> <uuid>` резервирует UUID. Ники сравниваются без учёта регистра.
3. Игрок заходит и регистрируется в течение [`reservationTtl`](#reservationttl). Новый аккаунт получает зарезервированный UUID, и резервирование расходуется.

`/identica admin reservation info <username>` показывает UUID, зарезервированный за ником, а `/identica admin reservation delete <username>` снимает резервирование.
В режимах `RANDOM` и `OFFLINE` резервирование заменяет UUID, который назначил бы режим; `PREMIUM` всегда назначает UUID лицензионного аккаунта.
`/identica admin clear <username>` резервирует за ником собственный UUID аккаунта, так что при повторной регистрации игрок сохранит свой UUID.

### reservationTtl

<Badge type="warning">Для опытных</Badge>

- Принимает: положительную длительность
- По умолчанию: `"15m"`
- Влияет на: то, как долго хранятся зарезервированные идентичности аккаунтов и резервирования ников

Это важно при регистрации, очистке аккаунта и для резервирований, заданных через `/identica admin reservation set`.
Резервирование ника истекает по прошествии этого времени, если за это время никто не зарегистрировался под этим ником.
Если значение слишком короткое, незавершённая регистрация может потерять зарезервированную идентичность.
Если слишком длинное, брошенные резервирования хранятся дольше.

<Tabs items={["YAML", "JSON"]}>
  <Tab value="YAML">
```yaml
identity:
  reservationTtl: "20m"
```
  </Tab>
  <Tab value="JSON">
```json
{
  "identity": {
    "reservationTtl": "20m"
  }
}
```
  </Tab>
</Tabs>

## sessions

`sessions` управляет поведением активных сессий подключённых игроков.

- поведение активных сессий подключённых игроков

Сессия существует, пока игрок в сети.

### concurrencyPolicy

<Badge type="warning">Осторожно</Badge>

- Принимает: `"REPLACE_EXISTING"` или `"REJECT_NEW"`
- По умолчанию: `"REPLACE_EXISTING"`
- Влияет на: политику открытия сессий по умолчанию, которую использует `SessionService.open(session)`

У аккаунта одна сессия, и она принадлежит подключению, которое её открыло.
Вход с того же подключения продолжает его сессию; политика определяет, что происходит, когда аккаунт входит с другого подключения, пока у него есть сессия, например через второй прокси, использующий тот же Redis:

- `REPLACE_EXISTING`: оставить новую сессию и отключить подключение, которое держало прежнюю, с сообщением `engine.concurrentLoginKick`, на каком бы прокси оно ни находилось
- `REJECT_NEW`: оставить прежнюю сессию и отклонить новый вход с сообщением `engine.concurrentLoginRefused`

Выход игрока закрывает только сессию его собственного подключения. Подключение, чью сессию заменили, больше не держит сессию, поэтому его выход не завершает сессию, которая её заменила.

Любое другое значение останавливает запуск с ошибкой, в которой указаны само значение и допустимые значения; файл при этом не меняется.

Политика касается подключений, которые уже вошли. Подключение, которое ещё входит, когда другое подключение аккаунта завершает вход, отключается при любой политике; см. [Входы в процессе](../engine/index.mdx#logins-in-progress).

`REJECT_NEW` не продолжает отклонять входы из-за сессии, которую больше никто не держит. Сессия прокси, который остановился или упал, не закрыв её, исчезает через [`replication.heartbeatTimeout`](../replication/index.mdx#heartbeattimeout), а прокси, который держит подключение, считает его сессию завершённой, как только это подключение перестаёт быть в сети.

Эта политика по умолчанию применяется, когда сессия открывается после аутентификации, регистрации или миграции.
Если одному провайдеру нужно другое поведение, задайте для него `providers.session.concurrencyPolicy` в конфигурации провайдеров.

<Tabs items={["YAML", "JSON"]}>
  <Tab value="YAML">
```yaml
sessions:
  concurrencyPolicy: "REPLACE_EXISTING"
```
  </Tab>
  <Tab value="JSON">
```json
{
  "sessions": {
    "concurrencyPolicy": "REPLACE_EXISTING"
  }
}
```
  </Tab>
</Tabs>

## listeners

Настройки слушателей определяют, регистрируются ли выбранные слушатели платформы и с каким приоритетом.
Классы слушателей и детали регистрации зависят от используемой интеграции с платформой.

### events

<Badge type="warning">Для опытных</Badge>

- Принимает: словарь, ключами которого служат полные имена классов событий
- Влияет на: регистрацию и приоритет соответствующих слушателей

#### register

<Badge type="warning">Осторожно</Badge>

- Принимает: `true` или `false`
- Влияет на: то, регистрируется ли этот слушатель события вообще

Если установить `false`, Identica не будет регистрировать этот слушатель.
Это может пригодиться для экспериментов с интеграцией, но может и сломать части процесса входа.

#### priority

<Badge type="warning">Для опытных</Badge>

- Принимает: `"LOWEST"`, `"LOW"`, `"NORMAL"`, `"HIGH"` или `"HIGHEST"`
- Влияет на: приоритет слушателя Identica для этого слушателя, который затем сопоставляется с моделью приоритетов событий текущей платформы

Если запись события есть, но приоритет не задан, текущий код использует `NORMAL`.
