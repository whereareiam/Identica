Конфигурация репликации определяет, как Identica разделяет состояние между несколькими экземплярами.

Когда репликация выключена, Identica использует пустой адаптер репликации, который ничего не делает.
Это значит, что чтение реплицируемых данных возвращает пустой результат, запись игнорируется, а каналы publish/subscribe бездействуют.

## enabled

- Принимает: `true` или `false`
- По умолчанию: `false`
- Влияет на: считается ли доступным адаптер репликации на основе Redis

Устанавливайте `true`, только если вам действительно нужно общее состояние между экземплярами и у вас настроен настоящий Redis.

## serverId

<Badge type="warning">Осторожно</Badge>

- Принимает: строку
- По умолчанию: случайно сгенерированная строка UUID
- Влияет на: как этот экземпляр обозначает себя в реплицируемых событиях и при другой координации между экземплярами

У каждого экземпляра в одной среде должен быть собственный постоянный `serverId`.
Если вам нужно предсказуемое поведение общего состояния, не оставляйте случайно сгенерированное значение, которое меняется между перезапусками.

Особенно важно это значение для реплицируемых событий: по нему Identica отличает события, возникшие локально, от событий, пришедших от другого экземпляра.
Кроме того, сессия запоминает `serverId` прокси, на котором находится подключение игрока, поэтому одновременный вход через другой прокси отключает именно это подключение.

## heartbeatTimeout

<Badge type="warning">Для опытных</Badge>

- Принимает: длительность не меньше `"3s"`
- По умолчанию: `"30s"`
- Влияет на: то, как долго запись, которой владеет этот прокси, хранится после того, как прокси в последний раз её продлил

Прокси владеет двумя видами общих записей: сессией каждого игрока, подключённого через него, и удержанием имени каждого игрока, который через него входит. Пока прокси ими владеет, он продлевает каждую из них каждую треть этого времени — при значении по умолчанию раз в 10 секунд.

Запись завершается сразу, как только прокси она больше не нужна: сессия — когда игрок отключается, удержание имени — когда вход завершается, игрок уходит или проходит [`pipelineTtl`](../engine/index.mdx#pipelinettl) сценария. Эта настройка важна только тогда, когда прокси останавливается, не завершив свои записи, например при падении. Тогда его записи исчезают через это время после остановки. До этого другие прокси всё ещё их видят: показывают сессии в `/identica admin session list`, `REJECT_NEW` по-прежнему отклоняет новые входы этих аккаунтов, а игрок с другого адреса под именем, под которым шёл вход, по-прежнему получает отказ `engine.usernameHeld`.

С репликацией через Redis одно продление — это одно чтение и одна небольшая запись на запись, то есть три команды Redis, а каждое десятое продление сессии вдобавок обновляет две её индексные записи. Для 1000 игроков в сети это около 360 команд Redis в секунду. Более короткий тайм-аут быстрее освобождает аккаунты и имена упавшего прокси и пропорционально увеличивает число команд; более длинный — уменьшает его.

Значение меньше `"3s"` отклоняется при запуске. Это не длительность офлайн-запоминания входа (remember-me).

## redis

Раздел `redis` определяет, как Identica подключается к Redis и какие каналы используются для репликации через publish/subscribe.

### host

- Принимает: строку
- По умолчанию: `"localhost"`
- Влияет на: хост Redis, который использует адаптер репликации Redis

### port

- Принимает: целое число
- По умолчанию: `6379`
- Влияет на: порт Redis, который использует адаптер репликации Redis

### credential

- Принимает: строку
- По умолчанию: `""`
- Влияет на: пароль Redis, используемый при подключении

Если значение пустое, Identica подключается к Redis без пароля.

### ssl

- Принимает: `true` или `false`
- По умолчанию: `false`
- Влияет на: использует ли подключение к Redis SSL/TLS

### timeout

- Принимает: целое число
- По умолчанию: `0`
- Влияет на: тайм-аут клиента Redis, передаваемый в пул Jedis

### channels

Раздел `channels` задаёт имена каналов Redis pub/sub, которые использует репликация.

Все экземпляры, которые должны работать в одной среде репликации, обязаны использовать одинаковые имена каналов.
В большинстве случаев значения по умолчанию лучше не менять — разве что возник конфликт имён или вы намеренно хотите разделить среды.

#### accountUpdates

<Badge type="warning">Для опытных</Badge>

- Принимает: строку
- По умолчанию: `"identica:accounts"`
- Влияет на: канал для реплицируемых событий, связанных с аккаунтами

#### sessions

<Badge type="warning">Для опытных</Badge>

- Принимает: строку
- По умолчанию: `"identica:sessions"`
- Влияет на: канал для репликации, связанной с сессиями

#### conflicts

<Badge type="warning">Для опытных</Badge>

- Принимает: строку
- По умолчанию: `"identica:conflicts"`
- Влияет на: канал для репликации, связанной с конфликтами

#### events

<Badge type="warning">Для опытных</Badge>

- Принимает: строку
- По умолчанию: `"identica:events"`
- Влияет на: общий канал реплицируемых событий

Если `events` задан, Identica использует его для общих реплицируемых событий.
Если значение пустое, текущий мост событий использует `sessions`.

## cache

Раздел `cache` задаёт имена общих пространств имён, которые используют реплицируемые кэши.

Все экземпляры, которые должны работать в одной логической среде Identica, обязаны использовать одинаковые значения пространств имён.
В большинстве случаев значения по умолчанию лучше не менять — разве что пространства имён пересекаются или вы намеренно хотите изолировать несколько сред в одном экземпляре Redis.

#### reservations

<Badge type="warning">Для опытных</Badge>

- Принимает: строку
- По умолчанию: `"identica:reservation"`
- Влияет на: пространство имён для репликации резервирования аккаунтов

#### instructions

<Badge type="warning">Для опытных</Badge>

- Принимает: строку
- По умолчанию: `"identica:handshake-instructions"`
- Влияет на: пространство имён для репликации инструкций рукопожатия (handshake)

#### pipelineState

<Badge type="warning">Для опытных</Badge>

- Принимает: строку
- По умолчанию: `"identica:pipeline-state"`
- Влияет на: пространство имён для общего состояния незавершённых конвейеров

Пароли, которые вводят игроки, никогда не записываются в это пространство имён. Пока регистрация ждёт повторного ввода пароля, здесь хранится его хеш.

Состояние подключения изменяется только поверх версии, которую прочитала Identica, поэтому прокси никогда не перезаписывает то, что другой прокси тем временем сохранил для того же подключения; см. [Одновременная запись](#concurrent-writes).

#### attempts

<Badge type="warning">Для опытных</Badge>

- Принимает: строку
- По умолчанию: `"identica:provider-attempts"`
- Влияет на: пространство имён для репликации попыток через провайдеры

#### sessions

Сессия хранится один раз — как запись под собственным идентификатором, — а найти её по аккаунту или по субъекту провайдера можно через индексные записи со списками идентификаторов сессий. Подраздел `sessions` задаёт имена трёх пространств имён.

##### records

<Badge type="warning">Для опытных</Badge>

- Принимает: строку
- По умолчанию: `"identica:sessions:records"`
- Влияет на: пространство имён записей сессий с ключом по идентификатору сессии

Запись истекает через [`heartbeatTimeout`](#heartbeattimeout), если прокси, на котором находится подключение этой сессии, не запишет её снова.

##### accounts

<Badge type="warning">Для опытных</Badge>

- Принимает: строку
- По умолчанию: `"identica:sessions:accounts"`
- Влияет на: пространство имён индексных записей со списками идентификаторов сессий аккаунта, с ключом по UUID аккаунта Identica

##### subjects

<Badge type="warning">Для опытных</Badge>

- Принимает: строку
- По умолчанию: `"identica:sessions:subjects"`
- Влияет на: пространство имён индексных записей со списками идентификаторов сессий субъекта провайдера

Индексная запись — всего лишь указатель. Identica сверяет каждый перечисленный в ней идентификатор с записями сессий и удаляет те, чьих записей уже нет, поэтому устаревшая индексная запись никогда не покажет завершившуюся сессию.

## Одновременная запись [#concurrent-writes]

Один и тот же игрок может в один момент попасть на два прокси, например переподключившись с того же адреса, пока вход на другом прокси ещё записывается. Identica записывает прогресс входа подключения и сессии аккаунта только поверх того, что прочитала: короткий Lua-скрипт сохраняет новое значение только пока в Redis всё ещё лежит прочитанное Identica значение, или ничего, если Identica ничего не нашла, за один атомарный шаг, и обновляет индекс ключей пространства имён так же, как обычная запись.

Если другой прокси записал раньше, прокси, который оказался вторым, не перезаписывает его и сам не повторяет попытку. Обслуживаемое им подключение отключается с сообщением `engine.concurrentChangeKick`, которое просит игрока переподключиться; следующий вход продолжается с того, что записал другой прокси, и подчиняется `settings.sessions.concurrencyPolicy`, как обычный более поздний вход. Изменения индексных записей сессий применяются заново поверх того, что записал другой прокси, поэтому ни один идентификатор сессии не теряется.

Identica запускает эти скрипты через `EVALSHA` и отправляет только дайджест скрипта. Если Redis отвечает `NOSCRIPT`, потому что перезапустился или его кеш скриптов был очищен, Identica загружает скрипт через `SCRIPT LOAD` и запускает его снова, поэтому на стороне Redis скрипты готовить не нужно. Пользователю ACL для Identica нужны команды `evalsha` и `script`.

Без Redis прокси хранит эти значения в памяти и сравнивает их так же, поэтому правило действует и на одном прокси.

## Поведение при подключении [#connection-behavior]

Когда репликация включена, провайдер пула Redis сразу пытается создать и проверить подключение к Redis.
Если подключиться не удалось, адаптер Redis становится недоступен, и операции во время работы переходят на пустое поведение, которое предоставляет стандартная обёртка адаптера репликации.
