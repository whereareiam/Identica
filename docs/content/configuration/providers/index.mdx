The providers configuration controls which identity providers are enabled and how provider-specific behavior is applied.
Use this file to enable providers, set priority and entrypoints, tune provider-specific session behavior, and apply feature-owned provider fields.

Shared feature settings and provider-scoped feature overrides are documented under [Features](../features/index.mdx).
Conflict configuration for provider-owned conflicts is documented under [Conflicts](./conflicts.mdx).

## behavior

`behavior` contains shared runtime timings for all providers.

### attemptTtl

<Badge type="warning">Advanced</Badge>

- Takes: a positive duration
- Current default: `"10m"`
- Affects: how long provider-attempt markers stay in the replicated attempt store

Identica uses this when it marks that a provider attempt already happened for a provider, scope, username, and IP combination.
Longer values make repeated attempts stay blocked longer.
Shorter values let retries happen sooner.

<Tabs items={["YAML", "JSON"]}>
  <Tab value="YAML">
```yaml
behavior:
  attemptTtl: "10m"
```
  </Tab>
  <Tab value="JSON">
```json
{
  "behavior": {
    "attemptTtl": "10m"
  }
}
```
  </Tab>
</Tabs>

## providers

- Takes: a list of provider entries
- Affects: provider enablement, ordering, provider selection by hostname, provider-specific session behavior, feature-owned provider overrides

Provider ids should match installed provider descriptors, such as `premium` or `credential`.

<Tabs items={["YAML", "JSON"]}>
  <Tab value="YAML">
```yaml
providers:
  - id: "premium"
    displayName: "PR"
    enabled: true
    priority: 100
    entrypoints:
      - "premium.example.com"
    session:
      concurrencyPolicy: "REJECT_NEW"
```
  </Tab>
  <Tab value="JSON">
```json
{
  "providers": [
    {
      "id": "premium",
      "displayName": "PR",
      "enabled": true,
      "priority": 100,
      "entrypoints": ["premium.example.com"],
      "session": {
        "concurrencyPolicy": "REJECT_NEW"
      }
    }
  ]
}
```
  </Tab>
</Tabs>

### id

- Takes: a provider id string
- Affects: which installed provider descriptor this entry configures

This should match the provider's descriptor id exactly enough for case-insensitive lookup.

### displayName

- Takes: a string
- Current default: `""`
- Affects: the user-facing label used for this provider when one is needed

If this is blank, Identica falls back to the provider descriptor name and then the raw id.

### enabled

- Takes: `true` or `false`
- Affects: whether the provider is available for resolution and flow building

### priority

- Takes: an integer
- Affects: ordering when multiple providers are eligible

Higher values win before lower values.

### entrypoints

- Takes: a list of hostnames, optionally with `:port`
- Current default: one example hostname per provider, which you replace with your own
- Affects: which provider a player picks by typing a hostname

Entries use the format `host` or `host:port`. A player picks the provider by joining through the hostname the client announces, for example `credential.example.com`; an entry with a port only matches that port. When several providers list the same hostname, the one with the higher `priority` picks it.
Leave the list empty if players should not pick a provider by hostname.

A hostname chooses among the providers the player may use. What it decides:

| Player | Interactive journey | Seamless journey |
|---|---|---|
| New player | The provider choice is skipped and the hostname's provider is used, if it is one of the providers the choice would offer. Otherwise the player chooses as usual. | The hostname's provider is tried first, then the others by `priority`. |
| Player with an account | Signs in with the hostname's provider if the account already uses it, otherwise with the account's own provider. | Same as interactive. |

What a hostname never does:

- It never lifts another provider's protection of a username. A provider refuses or challenges a connection before any provider is chosen, whatever hostname the player used. With Premium, a username that belongs to a premium account must still complete the premium login in a seamless journey, and an account that uses Premium must always complete it. Joining through the Credential hostname does not let an offline client register a premium player's name. The owner of the premium account, who completes the premium login, may register with Credential through that hostname.
- It never moves an existing account to a provider it does not use. A player changes providers with the provider's migration command, such as `/premium` or `/credential`.
- It never routes the player to a server. Entrypoints only pick a provider. The proxy's own forced hosts decide where a player lands, and routing's [`forcedHosts`](../routing/index.mdx#forcedhosts) sends players to the forced host's server once they are done. One hostname can be both an entrypoint and a forced host.

A provider can also demand its own login from everyone who joins through its hostname. Premium does: through its hostname, an offline client cannot join at all.

Username conflicts between providers can additionally require a hostname; see [Username authority](../identity/username/index.mdx).

### session

Use `session` when one provider should behave differently from the global live-session defaults.

#### session.concurrencyPolicy

<Badge type="warning">Advanced</Badge>

- Takes: `"ALLOW_MULTIPLE"`, `"REPLACE_EXISTING"`, or `"REJECT_NEW"`
- Current default: absent
- Affects: how live-session replacement behaves for this specific provider

If this is absent, Identica uses `settings.sessions.concurrencyPolicy`.

### features

Use `features` for per-provider overrides of built-in behavior. Providers declare integration support through `supportedFeatures()`. Omitted settings inherit global defaults; explicit provider values override them.

- Takes: an object containing feature-owned configuration subtrees
- Current default: absent unless supplied by a feature
- Affects: provider-scoped overrides for selected features

The supported subtrees include:

- `features.recognition`: [Recognition](../features/recognition/index.mdx#provider-overrides)
- `features.restriction.join`: [Join restriction](../features/restriction/join/index.mdx#provider-overrides)
- `features.verification`: [Verification](../features/verification/settings/index.mdx#provider-overrides)

The `restriction-join` feature uses the nested `restriction.join` configuration path.
Provider ability IDs such as `authoritative-username` are code declarations, not configuration subtrees.
