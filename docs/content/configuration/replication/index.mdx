title: Replication
description: Field-by-field explanation of Identica's replication configuration area.

The replication configuration controls how Identica shares state across multiple runtimes.

When replication is disabled, Identica falls back to a no-op replication adapter.
That means replication-backed reads return empty data, writes are ignored, and publish/subscribe channels do nothing.

## enabled

- Takes: `true` or `false`
- Current default: `false`
- Affects: whether the Redis-backed replication adapter is considered available

Set this to `true` only when you actually want shared cross-instance state and have a real Redis environment configured.

## serverId

<Badge type="warning">Warning</Badge>

- Takes: a string
- Current default: a generated random UUID string
- Affects: how this runtime identifies itself in replicated events and other cross-instance coordination

Each runtime in the same environment should have its own stable `serverId`.
Do not leave a random generated value in place across restarts if you want predictable shared-state behavior.

This value is especially important for replicated events, because Identica uses it to distinguish local-origin events from events coming from another runtime.
A session also records the `serverId` of the proxy holding the player's connection, so a concurrent login through another proxy disconnects exactly that connection.

## heartbeatTimeout

<Badge type="warning">Advanced</Badge>

- Takes: a duration of at least `"3s"`
- Current default: `"30s"`
- Affects: how long a record this proxy owns stays stored after the proxy last renewed it

A proxy owns two kinds of shared records: the session of every player connected through it, and the hold on the username of every player who is logging in through it. It renews each of them every third of this time, every 10 seconds with the default, for as long as it owns them.

A record ends at once when its proxy is done with it: a session when its player disconnects, a username hold when the login ends, the player leaves or the scenario's [`pipelineTtl`](../engine/index.mdx#pipelinettl) passes. This setting only matters when a proxy stops without ending its records, for example when it crashes. Its records then disappear this long after it stopped. Until then other proxies still see them: they list the sessions in `/identica admin session list`, `REJECT_NEW` still refuses a new login of those accounts, and a player from another address is still refused with `engine.usernameHeld` under a username that was being logged in.

With Redis replication a renewal is one read and one small write per record, which are three Redis commands, and every tenth renewal of a session also renews its two index entries. For 1000 online players that is about 360 Redis commands per second. A shorter timeout frees the accounts and usernames of a crashed proxy sooner and costs proportionally more commands; a longer one costs fewer.

A value below `"3s"` is refused at startup. This is not an offline remember-me duration.

## redis

The `redis` section controls how Identica connects to Redis and which channels are used for publish/subscribe replication.

### host

- Takes: a string
- Current default: `"localhost"`
- Affects: the Redis host used by the Redis replication adapter

### port

- Takes: an integer
- Current default: `6379`
- Affects: the Redis port used by the Redis replication adapter

### credential

- Takes: a string
- Current default: `""`
- Affects: the Redis credential used during connection

If this is blank, Identica connects without a Redis credential.

### ssl

- Takes: `true` or `false`
- Current default: `false`
- Affects: whether the Redis connection uses SSL/TLS

### timeout

- Takes: an integer
- Current default: `0`
- Affects: the Redis client timeout passed into the Jedis pool

### channels

The `channels` section defines the Redis pub/sub channel names used by replication.

All runtimes that should share the same replication environment must agree on these channel names.
Most setups should keep the defaults unless there is a naming collision or a deliberate environment-separation reason to change them.

#### accountUpdates

<Badge type="warning">Advanced</Badge>

- Takes: a string
- Current default: `"identica:accounts"`
- Affects: the channel used for account-related replicated events

#### sessions

<Badge type="warning">Advanced</Badge>

- Takes: a string
- Current default: `"identica:sessions"`
- Affects: the channel used for session-related replication

#### conflicts

<Badge type="warning">Advanced</Badge>

- Takes: a string
- Current default: `"identica:conflicts"`
- Affects: the channel used for conflict-related replication

#### events

<Badge type="warning">Advanced</Badge>

- Takes: a string
- Current default: `"identica:events"`
- Affects: the generic replicated-events channel

When `events` is set, Identica prefers it for generic replicated events.
If it is blank, the current event bridge falls back to `sessions`.

## cache

The `cache` section defines the shared namespace names used by replicated caches.

All runtimes that should share the same logical Identica environment must agree on these namespace values.
Most setups should keep the defaults unless there is a namespace collision or you intentionally want to isolate multiple environments inside the same Redis instance.

#### reservations

<Badge type="warning">Advanced</Badge>

- Takes: a string
- Current default: `"identica:reservation"`
- Affects: the namespace used for account reservation replication

#### instructions

<Badge type="warning">Advanced</Badge>

- Takes: a string
- Current default: `"identica:handshake-instructions"`
- Affects: the namespace used for handshake instruction replication

#### pipelineState

<Badge type="warning">Advanced</Badge>

- Takes: a string
- Current default: `"identica:pipeline-state"`
- Affects: the namespace used for shared pending pipeline state

Passwords that players type are never written to this namespace. While a registration waits for the password to be repeated, it holds that password's hash.

#### attempts

<Badge type="warning">Advanced</Badge>

- Takes: a string
- Current default: `"identica:provider-attempts"`
- Affects: the namespace used for provider-attempt replication

#### sessions

A session is stored once, as a record under its own id, and found by account or by provider subject through index entries that list session ids. The `sessions` subsection names the three namespaces.

##### records

<Badge type="warning">Advanced</Badge>

- Takes: a string
- Current default: `"identica:sessions:records"`
- Affects: the namespace of the session records, keyed by session id

A record expires after [`heartbeatTimeout`](#heartbeattimeout) unless the proxy holding the session's connection writes it again.

##### accounts

<Badge type="warning">Advanced</Badge>

- Takes: a string
- Current default: `"identica:sessions:accounts"`
- Affects: the namespace of the index entries that list an account's session ids, keyed by Identica account UUID

##### subjects

<Badge type="warning">Advanced</Badge>

- Takes: a string
- Current default: `"identica:sessions:subjects"`
- Affects: the namespace of the index entries that list a provider subject's session ids

An index entry is only a pointer. Identica checks every id it lists against the records and drops the ids whose record is gone, so an outdated entry never shows a session that ended.

## Connection behavior

When replication is enabled, the Redis pool provider immediately tries to create and test a Redis connection.
If the connection fails, the Redis adapter becomes unavailable and runtime operations fall back to the no-op behavior exposed by the default replication adapter wrapper.
