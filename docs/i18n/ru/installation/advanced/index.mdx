Выберите этот способ, если состояние Identica должно сохраняться после перезапуска экземпляра, пока не истекло его время жизни (TTL), или если несколько экземпляров должны использовать одно и то же реплицируемое состояние.
Он подходит для сохранения состояния после перезапуска, общего состояния между экземплярами, продуманной маршрутизации и сред, которым нужна стабильная модель работы с несколькими экземплярами.
В текущей реализации общее состояние обеспечивается через Redis.

## Что охватывает руководство [#scope]

Это руководство охватывает задачи расширенной установки: общее состояние, сохранение состояния после перезапуска и маршрутизацию.
<Include src="../_partials/provider-scope.mdx" />

## Что предполагает этот способ [#what-this-path-assumes]

- сервер, на котором работает Identica, может подключиться к Redis
- вы хотите, чтобы сессии и состояние незавершённых конвейеров сохранялись после перезапуска или были общими для нескольких экземпляров
- вы готовы сохранять имена общего состояния в этой среде неизменными
- вы знаете реальные бэкенд-серверы, на которые экземпляр должен направлять игроков

Это руководство не требует развёртывания с несколькими прокси.
Репликация полезна и для одного экземпляра, если важно сохранять состояние после перезапуска.

Если реплицируемое состояние будут использовать несколько экземпляров, держите их на одной версии Identica и задайте каждому свой уникальный `serverId`.

### Зафиксируйте общее состояние как осознанный контракт среды [step]

Откройте сгенерированную конфигурацию `replication` и превратите сгенерированные значения по умолчанию в стабильное описание среды.

Два самых важных правила:

- `enabled` должно быть `true`
- `serverId` должен стать постоянным значением, которое вы выбрали сознательно, а не случайным значением, сгенерированным по умолчанию

Практичная отправная точка выглядит так:

```yaml
enabled: true
serverId: velocity-main

redis:
  host: redis.internal
  port: 6379
  credential: ""
  ssl: false
  timeout: 5000
```

Если второй экземпляр должен использовать ту же реплицируемую среду, оставьте у него те же параметры подключения к Redis, имена каналов и пространства имён кэша, но задайте другой `serverId`, например `velocity-fallback`.

### Не меняйте имена каналов и пространств имён кэша [step]

Как только среда начала использовать реплицируемое состояние, считайте эти имена частью её контракта:

- `redis.channels.*`
- `cache.*`

Именно их неизменность позволяет сессиям, резервированиям, попыткам и состоянию незавершённых конвейеров оставаться согласованными после перезапусков и между несколькими экземплярами.

Не переименовывайте эти ключи без веской причины, когда среда уже работает.
Если вам нужны имена, специфичные для среды, определите их до развёртывания и больше не меняйте.

### Замените целевые серверы по умолчанию реальными [step]

Откройте `routing` и приведите цели в соответствие с именами реально существующих бэкенд-серверов.
Значения по умолчанию — это лишь примеры.

<Include src="../_partials/routing-targets.mdx" />

Для сегментированной топологии хорошей отправной точкой будет такая конфигурация:

```yaml
defaults:
  step:
    target: auth
  complete:
    target: lobby
scenarios:
  registration:
    step:
      target: registration
  migration:
    step:
      target: migration
```

Используйте имена своих серверов, а не те, что приведены здесь.
В сгенерированной конфигурации маршрутизации `scenarios` пуст; добавляйте сценарии только тогда, когда сценарий должен отличаться от `defaults`.
Если одному шагу нужна особая маршрутизация, используйте переопределение для шага, а не меняйте весь сценарий:

```yaml
scenarios:
  registration:
    overrides:
      steps:
        your-step-id:
          target: auth
```

Так обычный маршрут сценария остаётся неизменным, а один конкретный шаг при этом может вести на другой сервер.

Если вам нужно что-то ближе к реальной расширенной конфигурации, можно также настроить повторные попытки и более точные цели.
Практичный пример выглядит так:

```yaml
defaults:
  step:
    target: auth
    attempts:
      mode: RETRY_ONCE
      maxAttempts: 2
      retryDelay: 1s
      consumeOnReached: false
      consumeOnExhausted: true
  complete:
    target: lobby
    attempts:
      mode: NONE
      maxAttempts: 1
      retryDelay: 0s
      consumeOnReached: true
      consumeOnExhausted: true
scenarios:
  registration:
    step:
      target: register
      attempts:
        mode: RETRY_ONCE
        maxAttempts: 2
        retryDelay: 1s
        consumeOnReached: false
        consumeOnExhausted: true
    complete:
      target: lobby
    overrides:
      steps:
        provider-selection:
          target: register-fallback
  migration:
    step:
      target: migrate
      attempts:
        mode: RETRY_ONCE
        maxAttempts: 3
        retryDelay: 2s
        consumeOnReached: false
        consumeOnExhausted: true
    complete:
      target: survival
```

В этом примере:

- `authentication`, `registration` и `migration` используют каждый свою цель для шагов
- при завершении игрок отправляется туда, где он должен оказаться после прохождения процесса входа
- повторные попытки включены для маршрутизации шагов, где временные проблемы с целевым сервером более вероятны
- один шаг регистрации переопределён на другой сервер без изменения всего сценария

Используйте такую конфигурацию, когда разные части процесса входа действительно должны выполняться на разных бэкенд-серверах.
Если ваша сеть проще, пусть и маршрутизация будет проще.
