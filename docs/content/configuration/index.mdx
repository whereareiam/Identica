This section explains Identica configuration as a set of concepts, not as one specific file syntax.
That is intentional: Identica can choose its config representation at runtime, so the important thing is understanding what each config area means first.

## Format-agnostic by design

Identica does not have to be documented as "the YAML plugin" or "the JSON plugin."
The runtime selects a configuration format from a marker file in the data directory, with `type=YAML` as the default behavior in the current codebase.
Some explanations include examples where that helps, while others stay descriptive when the setting type is simple enough without one.

Because of that, this documentation describes:

- what each configuration area controls
- how the pieces relate to each other
- when you should edit one config area instead of another

<Callout title="Setting flags" type="warn">
  Some settings are marked with flags such as <Badge type="warning">Advanced</Badge>, <Badge type="warning">Warning</Badge>, <Badge type="error">Danger</Badge>, or <Badge type="info">Reserved</Badge>.
  These flags show that a setting is intentionally configurable, but should be changed with more care than ordinary options. Unmarked settings are normal day-to-day configuration.
</Callout>

## What Identica writes back

On every start and reload Identica completes each document with the settings it lacks and writes it back. Your values are kept; comments are not preserved.

A list is taken as you wrote it, including an empty one: `[]` means "nothing", not "use the default". Remove the key to get the default list back.

## Reloading

`/identica admin reload` reads every document of the running proxy again: the core documents, those of features and identity guarantees, and those of every loaded provider. Documents a provider owns are read before the sections other parts add to them, as on startup. Messages and settings that are read when they are used, such as the prompts players see or a provider's attempt limits, apply to the next players without a restart. The database connection is opened at startup, so a change to the persistence document takes effect on the next start.

A document that cannot be read keeps the values it had, and the other documents are still reloaded. The command then answers with `commands.reload.error` from the messages document, whose `{error}` names each file that failed; it answers with `commands.reload.success` only when every document was reloaded. Identica does not rewrite a file it could not read, so you can fix it and reload again.

## Configuration version

The settings document starts with `_version`, and so does the `settings` document of each feature under `features/`, which counts the upgrades of that feature's documents. Identica uses them to upgrade the data directory when a new release changes the layout of a document, and it refuses to start on a directory written by a newer release. Do not edit or remove them, and keep them when you copy your configuration to another server.

Identica upgrades the data directories of Identica 2.2.1 and of the 3.0.0 development builds on their first start with this version. Every setting, message and command you changed moves to the place this version reads it from, and what has no place any more is removed. The documents of a provider, below `providers/` next to its jar, are not upgraded: a setting there whose name or place changed falls back to its default.

Before an upgrade changes a file, the file is copied to `.strata/backup/` in the data directory. Identica never reads these copies, so the `.strata` folder can be deleted at any time.

## Feature selection and settings

Feature settings live under `features/<id>/`, with join restriction nested under `features/restriction/join/`. Provider-specific overrides belong to `providers[].features` and inherit shared defaults. All features are compiled into Identica. See [Features](./features/index.mdx) for configuration.

## Common value formats

Across configuration areas, values commonly appear in a few recurring forms:

- durations such as `"30s"`, `"10m"`, `"2h"`, `"1d12h"`, or ISO-8601 values such as `"PT10M"`
- bare numbers for durations such as `10`, which the current duration adapter treats as minutes
- enum values written as uppercase strings such as `"RANDOM"` or `"REPLACE_EXISTING"`
- booleans such as `true` and `false`
- maps keyed by provider id, scenario id, stage id, step name, or fully qualified event class name

For clarity, quoted duration strings are the safest style to document and maintain.
