The providers configuration controls which identity providers are enabled and how provider-specific behavior is applied.
Use this file to enable providers, set priority and entrypoints, tune provider-specific session behavior, and apply feature-owned provider fields.

Shared feature settings and provider-scoped feature overrides are documented under [Features](../features/index.mdx).
Conflict configuration for provider-owned conflicts is documented under [Conflicts](./conflicts.mdx).

## behavior

`behavior` contains shared runtime timings for all providers.

### attemptTtl

<Badge type="warning">Advanced</Badge>

- Takes: a positive duration
- Current default: `"10m"`
- Affects: how long provider-attempt markers stay in the replicated attempt store

Identica uses this when it marks that a provider attempt already happened for a provider, scope, username, and IP combination.
Longer values make repeated attempts stay blocked longer.
Shorter values let retries happen sooner.

<Tabs items={["YAML", "JSON"]}>
  <Tab value="YAML">
```yaml
behavior:
  attemptTtl: "10m"
```
  </Tab>
  <Tab value="JSON">
```json
{
  "behavior": {
    "attemptTtl": "10m"
  }
}
```
  </Tab>
</Tabs>

## providers

- Takes: a list of provider entries
- Affects: provider enablement, ordering, entrypoint routing, provider-specific session behavior, feature-owned provider overrides

Provider ids should match installed provider descriptors, such as `premium` or `credential`.

<Tabs items={["YAML", "JSON"]}>
  <Tab value="YAML">
```yaml
providers:
  - id: "premium"
    displayName: "PR"
    enabled: true
    priority: 100
    entrypoints:
      - "premium.example.com"
    session:
      concurrencyPolicy: "REJECT_NEW"
```
  </Tab>
  <Tab value="JSON">
```json
{
  "providers": [
    {
      "id": "premium",
      "displayName": "PR",
      "enabled": true,
      "priority": 100,
      "entrypoints": ["premium.example.com"],
      "session": {
        "concurrencyPolicy": "REJECT_NEW"
      }
    }
  ]
}
```
  </Tab>
</Tabs>

### id

- Takes: a provider id string
- Affects: which installed provider descriptor this entry configures

This should match the provider's descriptor id exactly enough for case-insensitive lookup.

### displayName

- Takes: a string
- Current default: `""`
- Affects: the user-facing label used for this provider when one is needed

If this is blank, Identica falls back to the provider descriptor name and then the raw id.

### enabled

- Takes: `true` or `false`
- Affects: whether the provider is available for resolution and flow building

### priority

- Takes: an integer
- Affects: ordering when multiple providers are eligible

Higher values win before lower values.

### entrypoints

- Takes: a list of hostnames, optionally with `:port`
- Affects: which provider a player who joins through one of these hostnames gets, see [How a provider is picked](#how-a-provider-is-picked)

Entries must use the format `host` or `host:port`. An entry without a port matches the hostname on any port; an entry with a port matches only that port. When several providers list the same hostname, the one with the higher `priority` takes it.
Leave the list empty if provider hostnames are not part of your setup.

A hostname only picks a provider. It never routes the player to a server, which is what forced hosts and routing's [`forcedHosts`](../routing/index.mdx#forcedhosts) do, and it never lifts a provider's own protection of a name: Premium still demands its login for a premium name or a Premium account, whatever hostname the player used.

### session

Use `session` when one provider should behave differently from the global live-session defaults.

#### session.concurrencyPolicy

<Badge type="warning">Advanced</Badge>

- Takes: `"ALLOW_MULTIPLE"`, `"REPLACE_EXISTING"`, or `"REJECT_NEW"`
- Current default: absent
- Affects: how live-session replacement behaves for this specific provider

If this is absent, Identica uses `settings.sessions.concurrencyPolicy`.

### features

Use `features` for per-provider overrides of built-in behavior. Providers declare integration support through `supportedFeatures()`. Omitted settings inherit global defaults; explicit provider values override them.

- Takes: an object containing feature-owned configuration subtrees
- Current default: absent unless supplied by a feature
- Affects: provider-scoped overrides for selected features

The supported subtrees include:

- `features.recognition`: [Recognition](../features/recognition/index.mdx#provider-overrides)
- `features.restriction.join`: [Join restriction](../features/restriction/join/index.mdx#provider-overrides)
- `features.verification`: [Verification](../features/verification/settings/index.mdx#provider-overrides)

The `restriction-join` feature uses the nested `restriction.join` configuration path.
Provider ability IDs such as `authoritative-username` are code declarations, not configuration subtrees.

## How a provider is picked

Every join collects reasons for providers to handle it, and the strongest reason wins. Identica picks the provider once, while the player connects, and keeps it for the whole journey. From strongest to weakest:

1. **A pending migration.** The player confirmed a move to another provider, so the new provider is set up.
2. **An account of a verified login.** The provider proved that the client owns its identity, such as Premium after an online login, and that identity already belongs to an account. An existing account keeps its provider, so a hostname never moves an account.
3. **The hostname.** The player joined through one of the provider's [`entrypoints`](#entrypoints). Joining through a hostname is a deliberate choice.
4. **A verified login without an account.** The provider proved the client's identity, but no account uses it yet. The player registers with that provider unless a hostname picked another one.
5. **The player's choice.** The player chose the provider in the interactive provider choice. The choice is kept when the player reconnects before the registration ends.
6. **A matching name.** An account with the player's username uses the provider. Nothing about the client is proven by the name alone.
7. **Discovery.** The provider recognises the username, without proof.

Reasons of the same strength go to the provider with the higher `priority`. Only providers the journey may use can win: a hostname whose provider the journey does not offer is ignored, and a provider that fails for the player is left out for the rest of the journey.

What this means in practice:

- A new player who joins through a provider's hostname registers with that provider. In an interactive journey, the provider choice is skipped when the hostname's provider is offered.
- A player whose verified login already has an account keeps that account's provider, whatever hostname they use. A Premium account stays on Premium through the Credential hostname.
- A new player's hostname beats a verified login without an account. A premium owner who joins through the Credential hostname of a seamless network, and is asked for the premium login because the name is premium, still registers with Credential, and later joins ask for the Credential password. Through the Premium hostname, the same player registers with Premium.
- When a Credential account holds the name `Steve`, the real premium owner of `Steve` who joins through the Premium hostname is asked for the premium login and reaches his own Premium account, or registers one. Without that login, only the matching name speaks for a provider, so the player is asked for the Credential password.
