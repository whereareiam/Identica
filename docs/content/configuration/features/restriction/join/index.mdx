`features/restriction/join/` holds join restriction's `settings.yml`, `commands.yml` and `messages.yml`. [Join restriction](../../../../admins/features/restriction/join/index.mdx) explains how staff use it.

## settings.yml

```yaml
enabled: false
allow: []
resumeBypass:
  authentication: false
  registration: false
```

<Setting
  name="enabled"
  takes="`true` or `false`"
  default="`false`"
  affects="whether providers can be join-restricted, for every provider that does not set its own value"
  flag="advanced"
>

</Setting>

<Setting
  name="allow"
  takes="a list of signals: `linked`, `recognized`"
  default="`[]`"
  affects="which players still get through while a provider is restricted, for every provider that does not set its own list"
  flag="advanced"
>

`linked` lets players with an account at the provider through, `recognized` players that [recognition](../../../../admins/features/recognition/index.mdx) recognises. Listing `recognized` does not turn recognition on.

</Setting>

<Setting
  name="resumeBypass.authentication"
  takes="`true` or `false`"
  default="`false`"
  affects="whether a login that was already waiting when the restriction started may finish"
>

</Setting>

<Setting
  name="resumeBypass.registration"
  takes="`true` or `false`"
  default="`false`"
  affects="whether a registration that was already waiting when the restriction started may finish"
>

Neither lets new attempts through. The scenario must also allow resuming with [`allowResume`](../../../engine/index.mdx#allowresume).

</Setting>

## Per provider

Under `features.restriction.join` of a provider's entry in `providers/providers.yml`. Both fields fall back to the shared settings when absent, and the provider's [`features.restriction.enabled`](../index.mdx#featuresrestrictionenabled) must not be `false`.

```yaml
providers:
  - id: "credential"
    features:
      restriction:
        join:
          enabled: true
          allow:
            - linked
            - recognized
```

<Setting
  name="features.restriction.join.enabled"
  takes="`true` or `false`"
  default="absent"
  affects="whether staff can restrict this provider's joins"
  flag="advanced"
>

</Setting>

<Setting
  name="features.restriction.join.allow"
  takes="a list of signals: `linked`, `recognized`"
  default="absent"
  affects="which of this provider's players still get through while it is restricted"
  flag="advanced"
>

</Setting>

## commands.yml and messages.yml

The commands, `/identica admin provider restriction join enable|disable|status`, have the same fields as those in [`commands.yml`](../../../commands/index.mdx#commands). The `denied` message is what a refused player sees.
